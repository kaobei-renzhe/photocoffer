# 协作红线（违反即返工）

完整版与交付自查清单见 `docs/开发协作规则.md`。

## 动代码之前

- **大改先出方案**：界面或功能的重构、布局调整、交互重组、技术方案替换，先说清楚「① 改哪里（文件:行号）② 影响什么 ③ 什么风险 ④ **有没有不改的替代方案** ⑤ 怎么验收」，确认后再写代码。缺一项不算方案。
- **只改需求覆盖的文件**：看到无关问题记录不修，在交付说明里单列。`git diff --stat` 里每个文件都要能对应到需求条目。
- **同一文件不许并发写入**：动手前用 `git status` + 文件修改时间双重确认。发现目标文件被别人改过就**停下问，绝不覆盖**。
- **核心文件先备份**到 `.cache/backup-<文件名>-<时分>.tsx`（该目录已 gitignore），并说明怎么恢复。

## 动手之中

- **分批落地**：大改拆 2–3 批，每批自身可编译、可运行、可回滚。要能回答「只保留这一批，app 是什么样」。
- **不许用样式藏功能**：别用 `opacity:0` / `inert` / `aria-hidden` / `display:none` 掩盖层级或状态问题（本身是设计意图的自动隐藏浮层除外）。先问「键盘和读屏还能用吗」。
- **数据安全高于一切**：涉及导入、移动、覆盖、删除照片或其元数据，必须先说清「操作失败时数据会怎样」。不为测试通过而放宽容错。

## 收尾必做

- `npm run typecheck` + `npm test` 全绿，缺一不算完成。
- 性能优化必须带 **改前 / 改后 / 测量方法 / 什么规模会退化** 四组信息。禁止"我觉得更快了"。
- 引用的行号、函数名、变量名必须来自实际读取。不确定就说"需要确认"，**不许编**。
- 交付里写一行「Windows 影响 / Mac 影响」；没有 Mac 真机就写"静态检查通过，未实机验证"，不许默认"应该一样"。
