# 职责边界（设计侧 / 实现侧）

本项目由两侧协作：**设计侧**负责想清楚、写下来、验规格；**实现侧**负责改对、测过、发出去。

> 完整方案见 `docs/_internal/两个AI的分工协作方案.md`（不公开）。

## 双方各自负责什么

**设计侧独立完成（不交接）**

- 需求梳理、待办拆解、方案判断
- 文档（README / release notes / 方案文档）
- 纯配置（`.gitignore` / `.gitattributes` / CI 产物名）
- 仓库元信息、图片素材
- 只读诊断（跑测试看现状、分析 diff）

**实现侧独立负责**

- 重构、性能优化、测试编写、依赖升级
- 打包、签名、发布、推送
- **任何涉及用户照片数据（导入/移动/覆盖/删除）的逻辑**

**交接事项**

功能开发、交互改动、样式调整、数据结构变更 —— 由设计侧给出规格，实现侧落地。

## 收到交接时怎么做

1. 规格里应该包含：目标 / 文件:行号级改动点 / 关联影响 / 风险 / **明确不做** / 验收清单。
2. **有歧义先问，不要猜。** 猜错一次的成本高于问一句。
3. 「明确不做」的条目要严格遵守 —— 那是防止越界改坏别处的护栏。

## 动手前必做

```bash
git status --short
git diff --numstat <目标文件>
```

- `git diff` **为空但 status 显示 modified** → 是行尾符噪音，不是别人的改动，可以放心动。
- 目标文件有**真实**未提交改动 → **停下问，绝不覆盖**。

## 交付时必做

1. `npm run typecheck` + `npm test`（现有 214 个测试必须全绿）。
2. commit message 说明「改了什么、为什么」。
3. **一次只提交一件事**，别把无关文件混进来。
4. 顺手发现的问题**记录不修**，在交付说明里单列。

## 验收分工

| 层 | 谁 | 验什么 |
| --- | --- | --- |
| 1 | 实现侧 | 代码正确性（typecheck + test） |
| 2 | 设计侧 | 交付是否符合规格、有无越界 |
| 3 | 用户 | 产品是否好用 |

实现侧不评价产品决策，设计侧不替用户判断「好不好用」。
