### 为什么这个决定是稳的

| 检查项 | 结果 |
|---|---|
| 中文同名 App | **无**（本轮全部搜索中，唯一没撞到同类产品的描述性名字） |
| 品类渊源 | 「片匣」是胶片时代的真实器材概念，专业感自带，不是编出来的 |
| 功能可知性 | 高 —— 「片」「匣」两个实词，不用解释就知道装什么 |
| 与产品承诺的对应 | 匣 = 东西在自己手里（本地优先）；匣不改造内容物（原片不动）；从匣里取（挑片）；匣可交出去（交付） |
| 读音 | 4–2，先落再扬，收尾有余韵；弱点是「匣」偏软 |

### 关于读音偏软

这是已知的唯一弱点。但读音是可以被使用习惯覆盖的——「飞书」「少数派」「什么值得买」刚出来时都被人说拗口，用久了就顺了。真正致命的是**功能指向错误**（如「月相」会被当成拍月亮的工具），而「片匣」没有这个问题。

## 三、英文名策略（待定）

### 原则

中文名承担识别与检索，英文名只承担"好念、干净、可注册"。**不追求直译。**

先例：Eagle、Bridge、Linear 的英文名都不解释任何东西。

### 已排除

- `Stow` —— 微软商店同功能产品
- `Oriel` / `Obscura` / `Camera Lucida` / `Lumen` / `Luminar` / `Lightroom` —— 全部被占
- `Lunaris` / `Moonphase` / `Lunaria` —— Luna 家族在摄影语境里已被"月亮摄影规划工具"生态占据

### 待验证候选（造词 / 冷门词路线）

| 候选 | 来源 | 理由 |
|---|---|---|
| **Trove** | 英语"珍藏、宝库" | 5 字母、单音节偏短、有"发现好东西"的暗示 |
| **Capsa** | 拉丁语"匣/盒" | 与「匣」同义，古典质感，软件领域冷门 |
| **Lumo** | 造词（light 的词根变体） | 零语义负担、好念、好注册 |
| **Vela** | 拉丁语"帆"，也是星座名 | 短、轻、有方向感 |

**建议先验证 Trove 和 Capsa**，一个是母语词有含义，一个是拉丁语同义——都能和「匣」建立暗线联系。

### 4.1 必改

| 位置 | 现值 | 改为 |
|---|---|---|
| `package.json` → `productName` | `月相` | `片匣` |
| `package.json` → `build.appId` | `com.silvermoon.lunaris` | `com.silvermoon.pianxia`（见 4.2 警告） |
| `package.json` → `build.nsis.shortcutName` | `月相` | `片匣` |
| `package.json` → `name` | `lunaris` | `pianxia`（仓库名可暂不改） |
| 窗口标题 / 关于页 / 启动画面 | 月相 · Lunaris | 片匣 |
| `README.md` 全文 | 月相 | 片匣 |

### 4.2 两个必须处理的坑（改之前必读）

**坑 1：`productName` 决定 userData 路径**

Electron 的 `app.getPath('userData')` 默认是 `%APPDATA%\<productName>`。把 `月相` 改成 `片匣`，会导致**旧目录找不到**——`library.db`、`thumbnails/` 全部失联，用户打开以为是空图库。

**必须写迁移**（启动时执行一次）：

```ts
// 伪代码
const oldDir = path.join(app.getPath('appData'), '月相')
const newDir = path.join(app.getPath('appData'), '片匣')
if (existsSync(oldDir) && !existsSync(newDir)) {
  fs.renameSync(oldDir, newDir)
}
```

**坑 2：`appId` 改动会断掉任务栏分组与通知**

Windows 的 AppUserModelID 绑定 `appId`。改整个 `appId` 会让任务栏把它当成新应用、通知链断裂、自动更新失效。

**最小改法**：只换产品段，保留作者命名空间
`com.silvermoon.lunaris` → `com.silvermoon.pianxia`

### 4.3 现在还不必改

- 仓库名（GitHub 仓库可继续叫 lunaris，等内容稳定再改，改名会自动跳转）
- `publish.url`（还是占位符 `https://updates.invalid/lunaris`，本来就没分发）
- 数据表结构（无影响）

## 五、图标方向（基于「匣」）

### 要解决的三个历史问题

| 问题 | 来自哪一轮 | 解法 |
|---|---|---|
| 太抽象（C 形红块 + 白块，看不出是什么） | H2 | 让"匣"有完整的物件轮廓，不做减法过度 |
| 头重脚轻 | H 原版 | 缺口与内容垂直居中，上下色块面积接近 50:50 |
| 像饭盒 | 片盒命名 | **关键：缝里透出的是白色（照片），不是深色（空隙）** |

### 核心手法

> **不要画"盒子的缝"，要画"从缝里透出来的那张照片"。**

饭盒之所以像饭盒，是因为它闭合、完整、没有内容。匣之所以是匣，是因为**里面装着东西，而且能看见**。

所以几何上：中间那条横带必须是**白色（宣白 #FAF6EE）**，代表露出一截的照片边——而不是深色空隙。同样的形状，颜色一换，语义就从"分成两半的盒子"变成"装照片的匣"。

### 待渲染的变体

| 变体 | 几何 | 意图 |
|---|---|---|
| V1 等宽 | 上盖 / 白带 / 下身，三者等宽 | 最稳，最抗缩 |
| V2 上窄下宽 | 盖比身窄 8% | 更像真实的匣（盖扣不严） |
| V3 上宽下窄 | 盖比身宽 8% | 盖扣在身上，有厚重感 |

三者的 16px 降级方案：只保留「上块 / 白线 / 下块」三个元素，白线宽度不小于 512 画布的 48px（9.4%）。
