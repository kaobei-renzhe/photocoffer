# 1. 人像工作台：从「带筛选的图库」改成「专注人像的工作台」

## 1.1 诊断：三个结构错误（不是缺功能）

**错误一：三种不同性质的东西并排。**
`PortraitWorkspace.tsx:458-605` 的左栏里，`文件夹`（第 459-504 行）、8 组 facet（第 507-578 行）、`全部照片`（第 467-477 行）用同一套 `.side-item` / chip 样式并列。但它们的语义完全不同：

- **范围**（scope）：我这一场在哪儿看——整个图库 / 某个文件夹。
- **维度**（facet）：我怎么给照片分档——景别 / 光线 / 色调。
- **状态**（status）：系统对这批照片有没有把握——已确认 / 可能 / 待确认。

三者混在一列，用户无法形成「先定范围、再按维度分档、最后处理不确定的」这条作业线——所以他看到的是「一个带筛选的图库」。

**错误二：顶部那个「全部」开关，等于自我否定。**
`:397-428` 的分段开关（仅人像 / 全部）+ 默认值 `:62` `portraitOnly = true`。它的存在说明这个页面目前只是「图库 + 一个 portraitOnly 过滤器」。而「全部照片」这个入口在图库视图里已经有了（`Sidebar` 的「全部照片」）。**同一个概念在两个视图里各有一个开关，是主人问「为什么会有全部的选项」的直接原因。**

**错误三：维度不排序、不折叠、默认全展开。**
8 组 facet（`db.ts:394-401`：景别/视角/光线/天气/场景/色调/氛围/情绪）+ 文件夹 + 标签 + 自定义，一屏铺满约 600px 高度，第一组「景别」距离用户视线 200px 以上。而组与组之间只隔 `mb-4`（16px）。**「天气」排在第四位、「景别」在最上面但没被强调**——排在第一屏视觉重量最大的是「文件夹」。

**裁决一句话**：不要新增功能，把这三层拆开，把默认折叠做对，工作台的感觉就出来了。

## 1.2 信息架构重排：范围 / 维度 / 状态 三层分离

### 1.2.1 三层各归其位

| 层 | 内容 | 位置 | 理由 |
|---|---|---|---|
| **范围** | 整个图库 / 某个文件夹（含子文件夹） | 中栏工具条左侧一个下拉「范围：整个图库 ▾」 | 范围是「看哪一批」，属于结果集的限定，只影响一次作业的边界；它不该和维度抢同一列视觉重量。**默认 = 整个图库**（对应现在 `folderId = null`） |
| **状态** | 已确认 / 可能人像 / 待确认（+ 抽查被判无人） | 左栏顶部**常驻状态卡**（不可折叠） | 状态是「系统对照片的意见」，用户必须随时知道系统有多确定；它是纠错的入口，必须常驻且带数字 |
| **维度** | 景别 / 视角 / 光线 / 色调 / 情绪 / 氛围 / 场景 / 天气 + 自定义维度 | 左栏状态卡下方，**按序排列、可折叠、记忆展开状态** | 维度是「我怎么分档」，是可折叠的作业工具 |

### 1.2.2 「全部照片 / 仅人像」开关：删除

**裁决：删除 `PortraitWorkspace.tsx:396-428` 整个分段开关。**

理由三条：
1. 工作台的语义就是「人像」。一个工作台里提供「看非人像」的开关，等于说这个工作台不是工作台。
2. `先看全部照片` 这个兜底（`:647-652`）和「全部」开关是同一需求的两个入口，重复。
3. 用户要看全部照片时，正确动作是**回图库**（一条明确的路），而不是在同页切一个开关（一条让页面变形、状态难解释的路）。

**替代路径（三条，覆盖原来「全部」能满足的所有需求）**：
- 要看整库 → 工具条左侧「← 图库」返回（`:353-355` 已有，改名见第 4 章）。
- 要看某个文件夹的人像 → 「范围」下拉选文件夹。
- 要看被判为无人的照片（抽查漏检）→ 状态卡里的「被判无人 128」链接（低频，见 1.3.4）。

### 1.2.3 维度排序与默认折叠（裁决 + 理由）

**排序（改 `facets.sort`，不动数据、不删维度）**

| 新序 | 维度 | 首次默认 | 为什么在这个位置 |
|---|---|---|---|
| 1 | 景别 | **展开** | 挑片第一维度：特写/近景/中景/全景/远景/环境人像，**直接决定交付怎么分组**。它必须第一眼可见 |
| 2 | 光线 | **展开** | 决定「这张能不能用」：逆光/硬光/柔光。第二高频 |
| 3 | 视角 | 折叠 | 平视/俯拍/仰拍/过肩/侧脸 —— 属于编排期（选一组里的机位变化），不是逐张判断 |
| 4 | 色调 | 折叠 | 冷/暖/高调/低调/黑白/胶片 —— 属于**整组一致性**判断，通常在选完之后 |
| 5 | 情绪 | 折叠 | 笑/沉思/疏离/俏皮 —— 客户选片时的偏好维度，摄影师自己挑片用得少 |
| 6 | 氛围 | 折叠 | 温柔/冷峻/复古/清新 —— 与情绪重叠度高，靠后 |
| 7 | 场景 | 折叠 | 影棚/居家/街头/海边 —— 环境人像才用，作为补充 |
| 8 | 天气 | 折叠（**置底**） | 晴/多云/雨/雪 —— 人像语境里基本无用（除非环境人像/旅拍）。**降级而不是删除**：删维度会连带影响用户已有标记，风险高于收益 |

**明确不做「移出」**：把天气/场景「移出人像工作台」需要动 `facets` 的可见性字段，会影响图库视图与 XMP 往返。**降级为「折叠 + 置底」已经解决了 80% 的视觉噪音，且零数据风险。**（若主人坚持要移出，请走「维度可见性」开关，见 8.2 待确认。）

**默认折叠两条硬规则**：
1. 用户手动展开/收起的状态**按维度 id 记忆**（`localStorage: portraitFacetsOpen`，与现有 `openSections` 同机制）。
2. 折叠时**必须显示该维度已选中的数量 badge**（如「色调 2」），否则用户不知道折叠区里有没有在生效的条件 → 违反「系统状态可见」（Nielsen #1）。

**状态卡的三条硬规格（视觉 1B.13.1 已定稿，实施时不要自由发挥）**
1. **「待确认」用数字变色 + 6px 圆点，禁止底色**。底色在本语言里表示「选中/正在操作」，而待确认是**状态**；用底会与左栏选中行互相污染。
2. **阴影不是「浮起」，是「给 1.1 级分档补一条边界」**。`--panel` 对 `--bg` 只有 1.12，而卡内 hover 行 `--panel-2` 对 `--panel` 只剩 1.06 → 两档叠起来会糊平。所以改用 `--card`（对 bg 1.11、对 hover 行 1.20）+ `--shadow-1`。**这句话必须写进代码注释**，否则下一个人会按 R-G3（阴影只给浮层）把 `box-shadow` 删掉，卡片立刻散架。
3. **sticky 外层 wrapper 要给上 6 / 下 12 的内边距**，否则卡片阴影会被 `overflow-y: auto` 的滚动容器裁掉——这是 sticky 元素最常见的坑。
4. **末行的「模型已更新」附注**只在 `staleOverrides > 0`（有人工判定是在旧 `MODEL_TAG` 下做的）时出现。它是**告知不是警告**：人工结论仍然有效，所以不用 `--danger`、不用底色、不弹 toast，行高 28（附注档，不占 38 的数据行档）。点击进「人工判定 N 张」复核列表。详见 1.3.5 配套一。

**要点**：
- 状态卡在**任何滚动位置都常驻**（左栏 `sticky top-0`），因为待确认数是最后一步作业的入口。
- 组标题右侧的「清空」只在该维度**有选中项**时出现（渐进披露，不给空操作留位置）。
- 删除 `:514-530` 的「+ / 垃圾桶」两个 20×20 常驻按钮（**不达标热区 + 高频误触风险**）。新建/删除维度收进组标题的右键菜单 + 左栏底部「新建维度」。理由：删除一个维度是可逆但要二次确认的动作，不该做成每个组标题旁边的常驻图标。

## 1.3 识别纠错设计（回应问题 1）

### 1.3.1 根因：两个 fail-open（代码级）

`src/main/portrait.ts:198-222`：

```ts
let score = 0
let hasPerson = true            // ← ① 默认「有人」
let resolved = false
if (source) {                   // ← ② source 为 null 时整段跳过，hasPerson 保持 true
  try {
    score = await detectFile(source)
    hasPerson = score >= PERSON_THRESHOLD
    resolved = true
  } catch (error) { /* 只写日志 */ }
}
if (resolved) upsert.run(...)   // 失败不落库（这点是对的）
flags.push({ id, hasPerson, score })   // ← 但 UI 拿到的是 true
```

两条 fail-open 路径，都会让**非人像照片进入「仅人像」列表**：

| 路径 | 触发条件 | 频次估计 | 落库？ |
|---|---|---|---|
| A. 检测抛错 | 模型 session 创建失败、ONNX 输入形状异常、sharp 解码异常 | 低 | 否（下次重试） |
| B. **取不到源** | `sourceFor()`（`:141-145`）先找 `mid` 缩略图，没有就取原文件；两者都拿不到 → `null` | **高**：新导入还没生成缩略图的照片、RAW 缩略图生成失败、文件被移走（`missing` 标记前） | 否 |
| C. 分数落在灰区 | `score` 在 0.5 附近，DETR argmax=person 但其实是街道/汽车（COCO 的 person 类对「人形轮廓」敏感） | 中 | 是 |

**路径 B 是「天空/街道/汽车/建筑大量混入」最可能的成因**：它不报错、不落库、UI 照常显示，且批量导入后普遍存在。修复必须同时覆盖 A/B/C。

### 1.3.2 修复规则：三态 + 置信度分档

**主进程（改 `PortraitFlag`，`shared/types.ts:1152-1156`）**

```ts
export type PortraitVerdict =
  | 'person'      // 检测成功，score ≥ 0.80
  | 'likely'      // 检测成功，0.50 ≤ score < 0.80
  | 'no-person'   // 检测成功，score < 0.50
  | 'unresolved'  // 检测失败 / 取不到源 —— 天然落进「待确认」

export interface PortraitFlag {
  id: number
  verdict: PortraitVerdict     // 新增，权威结论
  score: number                // 保留（现状已有，但渲染层把它丢了）
  hasPerson: boolean           // 保留兼容：仅 person/likely 为 true
  reason?: 'error' | 'no-source'  // unresolved 时给出原因，供文案使用
}
```

`scanPortrait()` 的改法（三行）：
1. `let hasPerson = true` → **删掉**，改为 `let verdict: PortraitVerdict = 'unresolved'`。
2. `if (source)` 为假时**不改 verdict**（保持 `unresolved`），并在 `reason` 里填 `'no-source'`。
3. catch 分支填 `reason: 'error'`。

**阈值（`portrait.ts:23`）**
- `PERSON_THRESHOLD = 0.5` **保持不变**（它划分的是「有人 vs 无人」，实测人像 1.00 / 纯风景 0.27，0.5 位置正确）。
- 新增 `PERSON_CONFIRM = 0.80`（划分「确认 vs 可能」）。

> **诚实提示（给主人看的一句话）**：由于这版 DETR 的分数是**饱和型**（人像基本落在 0.99–1.00，风景落在 0.2–0.3），「可能人像」在真实数据里占比会很小。**分档的真正价值不在区分 0.6 和 0.9，而在于把「检测失败 / 取不到源」从「人像」里彻底拿出来**。这是修 bug，不是提精度。

**渲染层（改 `PortraitWorkspace.tsx:166-170`、`:191-195`）**

```ts
// 现状（:168）：只存布尔，score 被丢掉
for (const flag of flags) next[flag.id] = flag.hasPerson
```
改为存整个 flag（`Record<number, PortraitFlag>`），`shownItems` 改为：

```ts
const shown = items.filter((it) => {
  const f = flags[it.id]
  if (!f) return false                         // 未扫描 → 不进网格（进待确认）
  if (f.override === 1) return true            // 人工判为有人，最高优先级
  if (f.override === 0) return false
  return f.verdict === 'person' || f.verdict === 'likely'
})
```

**四条状态 → 三处归位的映射表**

| 判定 | 分数 | 进网格？ | 状态卡计数 | 缩略图角标 |
|---|---|---|---|---|
| `person`（确认人像） | ≥0.80 | ✅ | 已确认 | 无（默认态不装饰） |
| `likely`（可能人像） | 0.50–0.79 | ✅ | 可能人像 | 一个小圆点 + tooltip「可能不是人像」 |
| `no-person`（无人） | <0.50 | ❌ | 不计（可在「被判无人」抽查） | 无 |
| `unresolved`（待确认） | — | ❌ | 待确认 | 无（在队列里看） |

**关键裁决：`unresolved` 永不进主网格。** 这样「仅人像」列表里再也不会出现「从未被检测过」的照片——问题 1 从根上消失。代价是「待确认」可能很多（首次导入几千张时全是 unresolved），所以扫描中的照片**不计入待确认**（见下）。

### 1.3.3 扫描中的显示规则（避免列表跳动）

现状问题：`PortraitWorkspace.tsx:144-189` 每 20 张一批回填 `portraitFlags`，而 `shownItems` 是 `useMemo` → **每 20 张网格就重排一次**，用户正在看的照片会被顶走。

**规则三条：**

| 场景 | 行为 |
|---|---|
| 扫描进行中 | 已判定为 `person/likely` 的照片**追加到网格末尾**（append-only，按发现顺序）；不在中间插入、不重排 |
| 扫描进行中 | 未扫描的照片**不进「待确认」计数**（否则用户会看到一个不断缩小的巨大数字，焦虑且无意义） |
| 扫描完成后 | **不自动重排**。只在用户改变筛选/范围/维度，或点工具条「重新排序」时按正式排序规则排列 |

**顶部进度条文案**：`正在辨认人像 36 / 240`（不是「正在识别人像 36/240…」，见第 4 章）。位置：中栏工具条下方一条 44px 内联条（不是浮层），带 `aria-live="polite"`。

### 1.3.5 写库方案（✅ 已拍板：人工判定永久保留）

> **拍板（2026-11-16，team-lead）**：人工判定**永久保留**，模型升级不抹除人工结论。三列方案 + 三条配套（UI 提示、统计口径单列、迁移）全部定稿，不再是「待确认」。

**现状**：`db.ts:320-327`

```sql
CREATE TABLE IF NOT EXISTS person_flags (
  item_id INTEGER PRIMARY KEY,
  has_person INTEGER NOT NULL DEFAULT 0,
  score REAL NOT NULL DEFAULT 0,
  model TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);
```

**定稿方案（三列 + 最小改动 + 天然防覆盖）**：

```sql
ALTER TABLE person_flags ADD COLUMN override INTEGER;         -- NULL=未人工判定 / 1=有人 / 0=无人
ALTER TABLE person_flags ADD COLUMN override_at INTEGER;      -- 人工判定的时间
ALTER TABLE person_flags ADD COLUMN override_model TEXT;      -- 做这次判定时的 MODEL_TAG，用于提示「模型已更新」
CREATE INDEX IF NOT EXISTS idx_person_flags_override_model
  ON person_flags(override_model);                            -- 供「N 张人工判定仍是旧模型下做的」一次查出
```

**为什么「天然防覆盖」**：`scanPortrait` 的 upsert（`portrait.ts:187-195`）列清单是固定的——

```sql
ON CONFLICT(item_id) DO UPDATE SET
  has_person = excluded.has_person,
  score = excluded.score,
  model = excluded.model,
  updated_at = excluded.updated_at
```

它**只写这四个字段**，永远不会碰 `override` / `override_at` / `override_model`。所以重扫、换模型、重新导入都不会抹掉人的判断——**不需要任何额外的保护逻辑**，这是选「加列」而不是「单开一张表」的主要理由。⚠ 实施时**不要**为了「顺手统一」把这三个字段加进 upsert 的 SET 清单，那会让本方案立刻失效——请在这段 SQL 上方写注释。

**读路径权威值**：

```sql
COALESCE(override, has_person) AS has_person_final
```

渲染层拿到的 `verdict` 按此计算：`override = 1` → `person`（人工确认）；`override = 0` → `no-person`（人工排除）；`override IS NULL` → 按 `score` 分档（1.3.2）。

**配套一 · UI 提示（状态卡内一行）**

当 `COUNT(*) WHERE override IS NOT NULL AND override_model <> MODEL_TAG > 0` 时，状态卡底部出现一行：

```
模型已更新 · 12 张人工判定仍保留  查看 →
```

- 规格：11/`--faint`，行高 28（**不占 38 行高档**，它是附注不是数据行），与状态卡 padding 10 对齐；`查看 →` 是 `--accent-text` 文字按钮。
- 点击 → 进筛选「人工判定 N 张」列表（不是队列，这些照片已经有结论，用户只是复核）。
- **这行提示不阻断任何操作**：它不是警告（人工结论仍然有效），只是告知「你的判定是在旧模型下做的，可以复核」。所以**不用 `--danger`、不用底色、不弹 toast**。
- 模型与 `override_model` 一致时不显示（绝大多数时候不显示）。

**配套二 · `portraitStatus()` 统计口径：override 单列，不混算**

`portrait.ts:147-174` 的返回值扩展为（**保持旧字段不删，避免 IPC 破坏**）：

```ts
export interface PortraitStatus {
  modelReady: boolean
  modelBytes: number
  detected: number          // 保留：模型已判定过的总数（不含人工判定），旧调用方不受影响
  total: number
  /** 新增：三档分开报，UI 不再自己算 */
  confirmedByModel: number  // 模型判为人像（verdict person/likely）
  excludedByHuman: number   // 人工排除（override = 0）
  confirmedByHuman: number  // 人工确认（override = 1）
  staleOverrides: number    // 人工判定是在旧 MODEL_TAG 下做的（驱动配套一的提示行）
}
```

**为什么不混算**：状态卡要显示「已确认 214 / 可能 6 / 待确认 12」，如果 `detected` 是一个混合总数，UI 就得在渲染层做减法，而减法的两个数来自不同查询 → 迟早对不上。**让主进程一次算清三档，UI 只负责显示**。这也顺带满足验收项「状态卡的三个计数之和 + 被判无人 = 库内可检测总数（数字自洽）」。

> ⚠ 注意「已确认」在状态卡里的含义：它包含**模型确认 + 人工确认**（用户不关心是谁确认的）。但 `confirmedByHuman` 要单独拿到，因为「模型已更新」的提示行需要它。两者不矛盾：一个是展示口径，一个是溯源口径。

**其余两条**：
- 人工判定后 `score` **不清零**（保留「模型当初怎么说」用于回溯）。
- XMP 往返**首版不写人工判定**（本机偏好，写进 XMP 会污染别的软件；若要写需先定命名空间）。

**降级方案（仅在迁移受阻时）**：先只修 fail-open（`verdict` 四态），override 写库延后，人工纠正只在本次会话生效，并在队列里明示「本次有效，重扫后需重新确认」。这个降级很差，但比「看起来能纠正其实没落库」诚实。

**四条纪律**：
1. **一屏最多 1 个实底主按钮**（视觉 P1″）。「开始过待确认」与「加入选片」互斥出现，永不同框。
2. **卡内实底 chip 最多 2 组**。判定 / 去留 / 景别 三行里同一时刻最多两行有选中（如「判定=可能」+「去留=留用」）。三行全选会得到一张全是黄块的卡，把 P1″ 的 8% 面积预算在 252px 宽里一次花光——而且这三行本来就是「按需点一两项」的动作。
3. **「景别」快捷行只做当前第一优先维度**（不是 8 个维度全铺）。要给别的维度打标 → 左栏点该维度，右栏那一行跟着换。这样右栏始终只有 1 行 chip。
4. **不给「保存」按钮，但必须给「什么时候生效」**。所有打标即时落库 + `Ctrl/Cmd+Z` 撤销（沿用现状 `applyValue` 的即时写入模型）。那句 11px 提示不是装饰，是「没有保存按钮」的**补偿**——不给保存按钮就必须给一句生效说明，否则用户会怀疑自己没点上。同理：动作区吸底后卡中部会留一段空白（内容就那么点），**空白下方必须有这句提示**，否则会被读成「渲染没完成」。

### 1.5.2 卡片不随滚动移动

右栏固定 `overflow-y: auto`，卡内动作区底部 `sticky bottom-0`（主按钮永远在手边，因为选中后最常见的下一步是「加入选片」）。参考 PixCake：右侧动作区永远可见，这是它「少一步」的来源。

# 2. 图片查看器交互规则

> 视觉已裁决：**悬浮胶囊 44px（不占布局）+ Tab 键进入沉浸 + EXIF 三级**。本章只定**规则与时机**，不改形态与尺寸。

## 2.1 诊断复核（补一条视觉没提的）

视觉 5.1 已给出正确诊断（占位条淡出无收益、`useIdle` 监听 keydown 导致翻页必闪）。补三条代码级事实，供验收对照：

1. `Lightbox.tsx:125-127`：`idle` 由 `useIdle(2000)` 驱动；`useIdle` 在 `hooks/useIdle.ts:15-22` 监听 `pointermove` / `pointerdown` / **`keydown`**。
2. `:449-457` 的 ←→ 是通过 `window` 捕获阶段 keydown 实现的 → **翻页 100% 会 `wake()`**。
3. `:755-776` 的左右箭头额外做了 `idle ? 'opacity-15' : 'opacity-100'`，在一个已经不稳的状态上又叠了一层（视觉 5.3 已裁决改为「恒 0.35，hover 1」）。

**结论：不是「显示时机不对」，是「不该有任何自动隐藏」。** 下面给的是**状态模型**，不是调参。

## 2.2 显隐判定式（精确、无计时器主路径）

视觉裁决「常驻」，落地时最关键的是：**翻页绝不能改变任何可见性状态**。所以状态源里不能有任何「计时器 + 输入事件」的组合（那就是 `useIdle` 的做法）。

```ts
// ── 三个独立的状态源，各自只有一个写入者 ────────────────────────
const [immersive, setImmersive]   = useState(false)  // 只由 Tab / Esc 写
const [slideIdle, setSlideIdle]   = useState(false)  // 只由幻灯片计时器写
const [peekBand,  setPeekBand]    = useState(false)  // 只由 pointermove 几何判定写，且仅在 immersive 时生效

// ── 唯一的可见性判定（纯函数，无副作用）────────────────────────
const chromeVisible =
  immersive
    ? peekBand                    // 沉浸态：指针在上下「唤回带」里才显示
    : !slideIdle                  // 常规/幻灯片：幻灯片静止时才隐藏

// ── 唤回带（几何条件，无计时器）────────────────────────────────
// 上带：pointerY < 68（14 边距 + 44 胶囊 + 10 缓冲）
// 下带：pointerY > viewportH - 68
const peekBand = pointerY < 68 || pointerY > viewportH - 68
```

**逐条回答「显隐规则」：**

| 问题 | 答案 | 为什么这样不会再闪 |
|---|---|---|
| 何时出现？ | 常规浏览**永远显示**（`chromeVisible = true`）。仅两种例外：幻灯片静止、用户按 Tab 沉浸 | 常规路径上 `opacity` 恒为 1 → **没有任何 transition 被触发**，翻页不会造成视觉事件 |
| 何时淡出？ | 只有两种情况：① `slideshow && 3s 无键/指针/滚轮` → 60ms 淡出；② `immersive` 且指针离开上下唤回带 → 200ms 淡出 | 两者都是**用户主导的稀有事件**，不是「系统猜你不动了」 |
| 换图是否重置？ | **不重置任何可见性状态**。`useEffect [item?.id]` 只重置图片状态（zoom / pan / rotation / region / hint，视觉 5.5-4），**不碰** `immersive` / `slideIdle` / `peekBand` | 因为可见性不依赖当前照片，换图在数学上无法改变它 |
| 鼠标静止判定？ | **常规浏览下不存在**。不设 idle 计时器 | 没有计时器 = 没有「看久了突然消失」 |
| 键盘导航算不算操作？ | 幻灯片里算（任何 keydown 都 `slideTick+1` 并立即显示，0ms）；常规浏览里**无意义**（本来就显示） | 唯一需要在键盘侧处理的场景被限制在幻灯片 |
| 指针进入胶囊区域会怎样？ | 无变化（已显示）。只有**局部反馈**：胶囊 `background` 加深一档（120ms），不改 opacity | 局部反馈不参与可见性，不会引起整条闪烁 |
| 胶片条/档案面板打开时？ | 面板与胶囊是两条独立通道；面板打开不影响胶囊可见性。面板**不参与** `chromeVisible` | 现状 `idle` 与 `drawing`/`helpOpen` 耦合（`:126`），新模型彻底解耦 |

**为什么「幻灯片」可以例外**：幻灯片时用户确实「不在操作」（视觉 5.4 已裁决）。判定式：

```
slideIdle = slideshow
         && now - lastUserInput > 3000
         && !drawing && !helpOpen && !immersive
lastUserInput 的来源：keydown / pointermove / pointerdown / wheel（**不含**自动翻页）
```

自动翻页（`Lightbox.tsx:188-197` 的 `setTimeout`）**不更新 `lastUserInput`**——这条必须显式写进代码注释，否则下一个人会顺手把 `onNavigate` 加进「用户输入」，闪烁立刻回来。

## 2.3 Tab 沉浸模式

| 项 | 规则 |
|---|---|
| 进入 | `Tab`（**仅在查看器内**；主窗口的 Tab 必须保留给焦点遍历，视觉与 a11y 都要求） |
| 退出 | `Tab` 再按一次 / `Esc`（`Esc` 优先级见下）/ 关闭查看器 |
|  immersing 时隐藏什么 | 顶胶囊、底胶囊、左右箭头、提示浮层。**保留**档案面板（它不属于 chrome，是内容区） |
| 进入时若有浮层 | 先关掉 `helpOpen`（快捷键浮层）与 `hint`，再进沉浸。理由：浮层是「临时说明」，沉浸是「清除一切」 |
| 唤回 | 指针进入上/下 68px 唤回带 → 胶囊 200ms 淡入；离开 → 200ms 淡出。**无计时器、无「1.2 秒后才消失」** |
| 状态保持 | 会话内保持（切换照片、切换筛选不重置）。**关闭查看器时重置为 false**（下次打开不应还在沉浸态——用户可能忘了自己按过 Tab） |
| 沉浸态下的快捷键 | 全部照常（`←→` / `1-5` / `P/X/U` / `I` / `+/-` / `Z` / `Esc`）。沉浸只是「看不见 chrome」，不是「禁用功能」 |
| 提示 | 首次进入沉浸，屏幕中央 1.5s 显示「已隐藏工具栏 · 按 Tab 恢复」（`aria-live="polite"`，`prefers-reduced-motion` 时静态 3s） |

**`Esc` 的完整优先级链**（在现状 `Lightbox.tsx:393-422` 的基础上插入两级）：

```
正在输入（笔记/备注）      → 只 blur，不关任何东西
正在框选（drawing）        → 取消框选
档案面板打开               → 关面板
沉浸态                     → 退出沉浸          ← 新增（放在「关面板」之后、全屏之前）
全屏                       → 退全屏
其余                       → 关闭查看器
```

> 顺序依据「由内到外」：输入 → 局部模式 → 面板 → 沉浸 → 全屏 → 窗口。现状是「全屏 → 框选 → 面板」，框选在面板之前是对的（框选依赖面板），我保留了这个相对关系，只把「沉浸」插在面板之后、全屏之前。

## 2.5 EXIF 三级：L1 到底常驻哪几项

| 级 | 内容 | 位置与规格 | 依据 |
|---|---|---|---|
| **L1 常驻** | `f/2.8` · `1/250s` · `ISO 400` | 底胶囊左起。13/500，单位 11/`--lb-faint`；三组**固定宽 40 / 56 / 56**，组间 16 | **只放曝光三角**。理由：这三项是「这张能不能用」的唯一判据（虚焦/欠曝/高感噪点），每一张都要看。焦距不进 L1——它是镜头属性，整组照片通常不变，逐张读没有信息量 |
| **L2 常驻（一行，可点）** | `NIKON Z 8 · NIKKOR Z 85mm f/1.2 S` | L1 右侧 + 12px 间距 + 1px `--lb-rule` 分隔；12/`--lb-faint`；`max-width: 320px`；单行截断；**可点 → 档案·信息** | 器材是「环境信息」，看一眼确认「这组是 85 拍的」即可。**缺失时的 fallback 链**：机身 → 镜头 → 焦段（取第一个非空），拼成一行，仍是单行截断 → 不会抖动 |
| **L3 按需（移出底条）** | 尺寸 `6048×4032`、拍摄时间、焦段、色彩空间、其余 | → 档案面板「信息」Tab | `InfoTab.tsx:366-373` 已展示 机身/镜头/焦段/光圈/快门/ISO，只需补 `尺寸` 与 `拍摄时间` 两行 |

**L1/L2 三条硬规则**
1. **缺失值不塌陷**：`f/—`、`—`、`ISO —` 占位保留（视觉 5.5-5）。否则换到一张没 EXIF 的照片（截图/手机取消 EXIF/导出图）时整条会横向滑动。
2. **不做 tooltip**：L2 的点击目标是「打开档案」，不是「展开更多」。悬浮提示会让用户在一条本已很窄的胶囊上做二次探索。
3. **不做筛选联动**（点击 `f/2.8` 筛出同光圈）：这是 Lightroom 的 Library Filter，存照的筛选在左栏/工具条，查看器里加筛选会打断「看图」这个单一任务。

## 2.6 换图不抖动（视觉 5.5 的可测补充）

在视觉 5.5 六条之上补两条实测项：

7. **胶囊宽度不随内容变化**（视觉 1B.13.3-a 已修订）：顶胶囊 `max-width: 62%` 会让宽度随文件名长度变化 → 换图时胶囊宽度跳变，这是「抖动」的新变种。**定稿**：`width: 620px; max-width: 62%` + 内部 `truncate`。620 在 1440 窗下小于 62%（≈890），等效固定；只有窄窗才收缩，而那是 **resize** 事件，不是换图——「换图绝不改变任何可见性/尺寸」的纪律因此保住。
8. **沉浸态与幻灯片态的过渡时长不同**：沉浸 200ms、幻灯片 60ms、显示 0ms（幻灯片）/200ms（沉浸）。三个值时序不同是有意的（幻灯片要「立刻回来」，沉浸要「平滑」），Phase 3 不要统一成一个 `--motion`。

## 2.7 高风险交互与降级

| 风险 | 后果 | 降级方案 |
|---|---|---|
| 沉浸态下用户不知道如何退出 | 以为 App 卡死 | ① 进入时 1.5s 提示；② `?` 快捷键浮层里第一行写「Tab 退出沉浸」；③ 指针进上/下 68px 唤回带即恢复；④ `Esc` 有效 |
| 幻灯片自动翻页把 chrome 唤回 | 又闪 | 显式注释：自动翻页不更新 `lastUserInput`；验收项见 7.3 |
| 查看器里设了 drag 区 | 拖动平移图片会变成拖窗口 | **查看器内不设任何 `-webkit-app-region: drag`**（见 3.6） |
| Windows 原生三键覆盖在网页之上 | 胶囊/按钮被盖住点不到 | 顶胶囊居中 + 右上 140×36 禁区（视觉 4.5/1B.8）。验收见 7.4 |

| 全屏（F11） | Windows 全屏时 overlay 隐藏，条 `display: none`（视觉 4.4） |

# 4. 全局文案规范

## 4.1 语气定义

> **一句话定调：像一位话不多、但很懂摄影的助理——说事实、给动作、不解释机制。**

三条禁忌：

| # | 禁 | 反例（现状） | 为什么 |
|---|---|---|---|
| 1 | **机器进程语** | `读取中…`（8 处）、`加载中…`、`准备中…`、`进行中…`、`写入中…`、`评分中…` | 「读取」是磁盘动作，不是用户在做的事。用户只关心「还要多久」「能不能干别的」。要么给骨架屏（<400ms），要么给「正在 X，还有 Y」 |
| 2 | **系统视角的免责句** | `当前筛选下没有识别到人像，可以切到「全部」看看。` / `没有符合筛选条件的图片` / `当前条件下没有照片。` | 这是把内部状态机（筛选+人像检测两个条件叠加）翻译成句子丢给用户。用户不需要知道是哪个条件导致的，只需要知道「这里没有」和「下一步点哪儿」 |
| 3 | **中文界面里的英文/符号装饰** | 感叹号、`～`、emoji、`DETR-ResNet-50`、`facet`、`temp` 出现在正文 | 机制名（模型名/表名/字段名）只允许出现在「设置 → 关于」与日志里。产品正文里出现一次，用户就少一分信任 |

**必须遵守的四条正向规则**
1. **零人称优先**：能省主语就省（「正在辨认人像」而不是「我们正在为您识别人像」）。必须出现时用「你」，不用「您」。
2. **动词开头**：按钮与动作文案以动词起头（「加入选片」「放进文件夹」「移到回收站」），不用名词（「选片加入」「文件夹」）。
3. **数字与单位贴紧、等宽**：`342 张`、`41 MB`、`36 / 240`、`1/250s`。所有数字用 `tabular-nums`（视觉 R-M5）。
4. **确定性分级**：能确定就陈述（「已加入 8 张」）；不能确定就说不能确定（「还没检测」「没能读到」），**不要用「可能」去掩盖错误**（现状 `hasPerson = true` 就是代码层的同类问题）。

|---|---|---|---|---|
| 照片 | 「照片」/「图片」混用（`Gallery.tsx` 用「图片」，`Toolbar.tsx` 用「照片」） | **照片** | 一个 App 只能有一个词。摄影师说「照片」，不说「图片」 | 全站文案（约 20 处） |
| 结构化维度 | 「分类」（`PortraitWorkspace:513/586/602/343`、inspector tab「分类」） | **维度** | 「分类」在中文里等于「归类结果」（AI 自动打标）；用户手动定义的 景别/光线 是「维度」 | 人像工作台 + inspector tab（6 处） |

**四条披露规则**

| **R1 一屏一个主行动** | 每个视图在同一时刻只允许 1 个实底主按钮（视觉 P1″ 的延伸）。人像工作台 = 「加入选片」；空状态 = 「下载模型」/「开始过待确认」 | 见 1.5.1 |

## 4.5 三类状态的标准句式模板

| 类型 | 结构 | 范例（可直接用） |
|---|---|---|
| **空状态** | 【这里为什么是空的】+【一个动作】+（可选）【一句退路】。**标题 ≤14 字，副行 ≤30 字，最多 2 个按钮** | 人像 0 结果：「这个范围里还没有人像。」/「换个范围，或去「被判无人」抽查。」/〔换个范围〕〔抽查被判无人〕<br>图库空：「图库里还没有照片。」/「把照片或文件夹拖进来，或点下面的按钮。」/〔导入照片〕<br>待确认清空：「都确认完了。」/「接下来按景别挑片。」/〔按景别开始〕 |
| **错误** | 【发生了什么】+【你的照片没事（若为真）】+【一个动作】。**禁止在正文里出现 error.message 原文** | 读不出文件夹：「这个文件夹读不出来。」/「可能是权限不足，或磁盘已断开。照片没有动。」/〔重试〕〔换一个位置〕<br>模型下载失败：「模型没能下载完。」/「网络中断了，已下载的部分可以继续。」/〔继续下载〕<br>打标失败：「没能打上这个标记。」/「稍后会自动重试；如果一直失败，检查磁盘是否可写。」/〔重试〕 |
| **加载** | 【正在做什么】+【还有多少】。**<400ms 不显示任何文案；>400ms 才出现；有总数时不用「…」** | 首次读库：「正在打开图库…」（无总数 → 允许「…」）<br>辨认人像：「正在辨认人像 36 / 240」<br>导入：「正在导入 128 / 900 · 还有约 40 秒」<br>识图：「识图 36 / 240」 |
| **危险确认** | 【要做什么（明确对象与数量）】+【不可逆的部分】+ 按钮用**具体动词**，不用「确定/取消」 | 移到回收站（可撤销，不需确认，用 toast + 撤销）<br>彻底删除：「彻底删除 8 张照片的记录？」/「磁盘上的原图不会动，但索引、缩略图和标记会一起删掉，不能撤销。」/〔彻底删除〕〔保留〕<br>清空回收站：「清空回收站？」/「{n} 条记录与缩略图会被删掉，原图不动，不能撤销。」/〔清空〕〔保留〕<br>删除维度：「删除维度「景别」？」/「照片上的标记会保留。」/〔删除维度〕〔保留〕 |
| **成功反馈** | 【动作 + 数量】+（可撤销时）一个撤销入口。**不写「成功」二字** | 「已加入选片 8 张 〔查看〕」/「已留用 8 张 〔撤销〕」/「已标记 3 张 〔撤销〕」 |

**三条统一细则**
1. **按钮不用「确定/取消」**（除纯信息确认）；危险操作的右按钮永远是「保留」而不是「取消」，左按钮是具体动词。
2. **「撤销」窗口 10 秒**（现状 toast 无时限，需加）。超过 10 秒后动作不可撤销，toast 自动消失。
3. **文案里的数字必须和界面上的数字同源**（同一个 state），不允许文案里写死「约 41 MB」而代码里是 `MODEL_SIZE`（`portrait.ts:19` 已有常量，直接插值）。

### 4.5.1 危险色的用法（视觉 1B.13.5 实测登记，⚠ 工程必读）

文案层面「危险」只有两个强度，对应两种视觉语言。**实测推翻了一个常见写法**：

| 组合 | 实测对比度 | 结论 |
|---|---|---|
| 白字 on `--danger`（#F0664E/#F2604A） | **3.13** ❌ | |
| #F2F2F2 on `--danger` | 2.79 ❌ | |
| `--danger-text` on `--panel-3` | **6.60** ✓ | 淘汰等「可撤销」用它 |
| `--danger-text` on `--panel-2` | **7.33** ✓ | 错误提示条用它 |

**三条规则**：
1. **`--danger` 是前景色，不是填充底**。拿它当 background 再配白字，会做出「看起来很红很危险、实际看不清」的按钮——这是工程最容易犯的错。
2. **真正需要红实底的只有两处**：① 永久删除的最终确认 ② 清空回收站。这两处用视觉新增的 **`--danger-fill`**（G1 `#B33A2B` 白字 5.90 / G2 `#A62A21` 白字 7.06）。
3. **不存在 `--danger-soft` / `--danger-border`**（视觉已明令不建）。错误条/警告条一律 **`--panel-2` 底 + `--danger-text` 字 + 三角图标**（7.33:1）。不给 token，就不存在「到处乱用」的可能——这比写十条规范管用。

> ⚠ **迁移影响（工程必看）**：现有代码里 `--danger-soft` **23 处**、`--danger-border` **23 处**，散布在 **19 个文件**（`styles.css:44-45` 定义）。token 被删后这些 `bg-[var(--danger-soft)]` 会退化成透明。替换映射：
> `bg-[var(--danger-soft)]` → `bg-[var(--panel-2)]`；`border-[var(--danger-border)]` → 去掉描边（改由三角图标承担「这是错误」的语义）；`hover:bg-[var(--danger-soft)]`（`ContextMenu.tsx:90`）→ `hover:bg-[var(--panel-3)]`；`text-[var(--danger-text)]` 全部保留。

## 6.4 高风险 a11y 项（这三条最容易被跳过）

| 项 | 风险 | 做法 |
|---|---|---|
| 待确认队列 | 只能鼠标点三个按钮 → 键盘用户无法纠错 | 三个按钮都是普通 `button`，`Y/N/→` 是额外加速，不是唯一路径 |
| 沉浸模式 | 隐藏 chrome 后，屏幕阅读器用户失去上下文 | 沉浸时给 stage 一个 `aria-live="polite"` 的「已进入沉浸，按 Tab 退出」；胶囊用 `inert` 而不是 `opacity: 0`（`opacity:0` 的元素仍在可访问树里，会读到一堆看不见的按钮） |
| 拖拽排序（侧栏文件夹/标签） | 纯鼠标操作 | 每条支持 `Alt+↑/↓` 移动（现状无），至少保证右键菜单里有「上移/下移」 |

> **`inert` 这条要特别强调**：现状 `Lightbox.tsx:127` 用 `opacity-0 pointer-events-none` 隐藏 chrome，按钮**仍在 Tab 序列与可访问树里**。改成胶囊后同样的坑会重现——任何 `opacity: 0` 的隐藏必须配 `inert` 或 `visibility: hidden`。
