## 三、数据与升级（已修）

1. **迁移分步化**：`db.ts` 新增 `MIGRATION_STEPS`（v1 基础表、v2 数据安全列与附加表、v3 文件夹层级/人像/研读/选片），按 `PRAGMA user_version` 逐级执行，每步独立事务并写回版本号；报错带「第 N 步 / 子步骤」定位。
2. **备份失败中止**：非新库升级前 `VACUUM INTO` 失败会中止升级，不再「没备份也硬上」。
3. **FTS 先重建**：v1 建完 FTS 后立即 `rebuild`，修复老库升级时 UPDATE 触发 FTS delete 导致的 malformed 错误。
4. **恢复校验**：备份 `meta.json` 写入 `app: lunaris` 与 `userVersion`；恢复时拒绝其他应用与更新版本的备份，兼容旧 `image-nest` 标记。
5. **配置导入归一化**：`llm` 走 `normalizeLlmSettings + saveLlmSettings`（含旧结构镜像）；其他字段仍走 `updateConfig`；`statSync` 失败给出明确提示。
6. **机器路径剥离**：导出/导入时去掉 `pick.lastDir`、`finals.lastDir`、`autoBackup.directory`。
7. **回滚一致性**：`autoUpdater.allowDowngrade = true`；打包清理保留最近两个版本；README 补充 https 与回滚说明。
8. **工程化**：顶层 `files` 补 sharp 异平台排除；`engines.node >= 22` + `.nvmrc`；CI 增加对比度检查、`verify:dist`，并上传 `latest.yml` 与 `.blockmap`。
9. **类型去重**：`AutoBackupSettings`、`ClipProgress` 统一从 `shared/types` 导入。

## 四、性能（已修）

### 主进程

- `listItems`：总数缓存（图库 + filter 签名，2s TTL），翻页不再每页重算 COUNT；写操作主动 `invalidateItemTotals()`。
- `ai` 排序：相关子查询改为 `LEFT JOIN quality_scores`。
- 堆叠计数：逐个 COUNT 改为一次 `IN (...) GROUP BY`。
- `rescan` / `sync`：同步逐条 `statSync` 改为 64 并发异步 stat，分批提交，不再冻结主进程。
- 缩略图/原图协议：缓存已解析路径（4000 条上限，命中仍校验存在），只在命中请求档位时缓存，避免回退档位卡住高清更新。
- 分组：`cameraOf` 在单次 `buildGroupPlans` 内按行缓存，同一张图只解析一次 EXIF。

### 渲染层

- `Gallery`：拖拽回调 `useCallback`；过扫描 700 → 350；焦点滚动改用 ref，不再随列表加载把视图拽回；预加载 cleanup 清空 `src`。
- `App`：`handleSelect` 用 ref 保持稳定；列表 effect 用 filter 签名判断「筛选变了才回第一页」，展开分组时保留已加载条数；元数据/clipStatus/relocate 三个 effect 合并为 300ms 防抖。
- `Sidebar`：文件夹树、标签树、facet 取值分组改为 `useMemo`。
- `Toolbar`：缩略图滑杆本地值 + 150ms 防抖提交。
- `Lightbox`：预加载前后各一张原图。

## 五、3 万条基准（同机、5 次取中位数）

| 查询 | 结果 |
| --- | --- |
| `COUNT(*)`（带标签 EXISTS 过滤） | P50 9.90ms / P95 10.06ms |
| 首页（COUNT + 200 条） | P50 10.72ms / P95 10.90ms |
| 深页 offset 29800（旧：每页 COUNT） | P50 25.95ms / P95 26.56ms |
| 深页 offset 29800（新：复用总数） | P50 16.05ms / P95 16.27ms |
| `ai` 排序（旧：相关子查询） | P50 11.30ms / P95 12.11ms |
| `ai` 排序（新：LEFT JOIN） | P50 11.72ms / P95 11.92ms |
| 堆叠计数 30 组（旧：逐组查询） | P50 0.31ms / P95 0.43ms |
| 堆叠计数 30 组（新：一次 GROUP BY） | P50 0.30ms / P95 0.40ms |

结论：

- 深分页 QPS 提升约 **1.6×**，达到预期。
- `ai` 排序与堆叠计数在本机 SQLite 上收益接近 0：`quality_scores` 有主键，相关子查询本来就走索引；30 组堆叠的逐条查询也只有 0.3ms。改写保留（语义更清楚、避免 N+1 的规模风险），但不宣称提速。
- 若后续 `ai` 排序成为瓶颈，建议物化 `items.ai_score` 列并加索引（需要 schema v4），不要在 SQL 层继续绕。

复现：`node scripts/bench-review.mjs`。

## 七、明确未修 / 后续建议

1. **语义搜索 worker 化**：3 万×512 全量点积仍在主线程（实测约百毫秒级），改 worker 需要迁移向量缓存与取消机制，单独排期。
2. **备份 zip 流式化**：`readFileSync` 逐文件读入内存，大缓存备份峰值可达数百 MB；建议后续改成流式写入。
3. **选片 HTML 分片**：999 张 base64 内嵌到单个 HTML，内存与文件体积都大；建议改临时文件 + 相对引用。
4. **键集分页**：目前仍是 OFFSET，深页 16ms 可接受；要彻底解决需要改 `Api.listItems` 契约。
5. **导入 INSERT 事务**：每张图的首条 INSERT 仍是单条提交；patch 写入已经按 50 条事务批量。并发 worker 跨 await 无法安全共享事务，未改。
6. **AI 排序索引**：见第五节，建议物化分数字段。
7. **残留风险**：SSRF 的 DNS 校验与 fetch 之间仍有 rebinding 窗口；路径白名单只覆盖渲染层可传路径的入口，不防本机恶意进程。
8. **大重构未做**：App 状态拆分、tsconfig 拆 node/web、IPC 通道常量表、grouping 增量重算、thumbs 统计增量。

## 九、升级与发布注意事项

1. 老库首次用新版本打开会执行 v0→v3 迁移，迁移前自动 `VACUUM INTO` 备份；备份失败会中止升级。
2. 迁移会重建一次 FTS（只做一次，`meta.fts-rebuild-v3` 记录）；3 万张约数百毫秒到 1 秒。
3. 新版本备份的 `meta.json` 带 `userVersion`，旧版本恢复会拒绝更新版本的备份；向上兼容可恢复旧备份。
4. 更新源必须是 https；本机 mock 允许 http。回滚依赖保留最近两版安装包。
5. 升级 onnxruntime 后要重新验证 DLL 裁剪；本次已在最终包上复验。
