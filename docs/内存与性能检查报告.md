# 内存与性能检查报告

> 版本：0.4.1（拉取后的代码，dev 构建）
> 环境：Windows 10.0.26300 · Electron 45.0.0 · 显示缩放 175% · 临时空数据目录
> 数据：40 张真实 JPEG（1200×800）+ 直接写入 3 万条合成记录（只有元数据，无缩略图）
> 未覆盖：CLIP 语义索引与任何 AI 网络调用（本机未下载模型）

---

## 一、结论摘要

- **没有发现明显内存泄漏**：3 万条库下主进程 RSS 约 250 MB，渲染进程 JS heap 7–20 MB；灯箱关闭后 `dialog = 0`、`photo://` 图片归零，heap 回落到约 5 MB。
- **虚拟滚动正常**：3 万条滚到底，当前文档 DOM 始终在 500 个节点左右，渲染卡片 18–40 张；CDP `DOMCounters` 的跨文档增长不是应用泄漏。
- **查询在 3 万条下可接受**：首页 10 ms、搜索 21 ms；两个真正的瓶颈是 **AI 排序约 60 ms** 和 **深页 offset 约 40 ms**。
- **最大性能瓶颈是导入**：约 **5–6.5 张/秒**（155–203 ms/张），3 万张需要 77–100 分钟；根因是每张图 **两次完整解码**（1280 底图 + 原图 dHash）。
- 语义索引的内存未实测：按 3 万 × 512 维 float32 估算，向量本体约 61 MB，扩容后可能接近 90 MB，模型会话另计。

## 二、内存实测

### 2.1 3 万条库（40 张真实图）

| 指标 | 数值 |
| --- | --- |
| 主进程 RSS / heap / private | **250 MB** / 13 MB / 176 MB |
| 渲染进程 JS heap | **7.3 MB** |
| 当前文档节点 / 卡片 | 1257 / 40（含侧栏、工具栏、详情面板） |
| 灯箱打开时 | dialog 1、`photo://` 图 1、heap 5.4 MB |
| 灯箱关闭后 | dialog 0、`photo://` 图 0、heap **4.8 MB** |
| 进程树 Working Set | 主 461 MB + 渲染 264 MB + GPU 342 MB + utility 152 MB ≈ **1.2 GB** |

> Working Set 是各进程分别统计的，会把共享内存重复计算，不能当真实占用看；主进程 RSS 250 MB 更可信。
> GPU 342 MB 主要是 Chromium 合成与 175% 缩放，属于 Electron 基线，不是业务代码分配。

### 2.2 滚动与灯箱

| 阶段 | 当前文档节点 | 卡片 | JS heap |
| --- | --- | --- | --- |
| 初始 | 462 | 40 | 4.0 MB |
| 滚到 3 万条底部 | 437 | 35 | 5.1 MB |
| 灯箱打开 | 502 | 35 | 5.4 MB |
| 灯箱关闭 | 575 | 18 | 4.8 MB |

- 滚完 1.88 万像素、20 次跳转用时约 270 ms，600 ms 内记录到 87 帧，未见长卡顿。
- 关闭灯箱后 DOM 与 heap 都回落，未发现逐次累积。

### 2.3 一个容易误判的指标

CDP `Memory.getDOMCounters()` 在滚动后从 1257 涨到 3512，看起来像泄漏；但当前文档的 `document.getElementsByTagName('*')` 始终稳定在 437–575，`documents` 字段为 6。
增长来自 Chromium 的跨文档/分离文档统计，不是页面 DOM。**不要用 `DOMCounters.nodes` 判断这个应用的 DOM 泄漏**，要看当前文档节点数或 heap。

## 三、性能实测

### 3.1 启动

| 指标 | 数值 |
| --- | --- |
| 进程启动 → 欢迎页可交互 | **1.1 s** |
| 进程启动 → 图库可交互 | **2.4 s** |

### 3.2 导入

| 场景 | 耗时 | 单张 |
| --- | --- | --- |
| 首批 40 张（冷启动） | 6.19 s | 155 ms |
| 第二批 20 张（热身后） | 3.18 s | 159 ms |
| 之前一轮 120 张 | 24.4 s | 203 ms |

稳定在 **约 5–6.5 张/秒**。3 万张预计 **77–100 分钟**。

根因在 `src/main/importer.ts:478-482`：每张图 `Promise.all` 里同时做

- `prepareBase(source)`：解码原图生成 1280 底图；
- `computeDHash(source)`：又解码一次原图算 dHash。

两次完整解码 + 两次缩略图（mid/low）是主要 CPU 成本；RAW 还会写一份全尺寸预览。

### 3.3 查询（3 万条，IPC 端到端）

| 查询 | P50 | P95 | 说明 |
| --- | --- | --- | --- |
| 首页 200 条 | **9.6 ms** | 10.6 ms | 含 COUNT（2 s 缓存） |
| 深页 offset 29600 | **37.8 ms** | 42.7 ms | OFFSET 需要跳过 2.96 万行 |
| 搜索 `photo-29`（约 1000 命中） | 17.8 ms | 21.2 ms | FTS + 映射 |
| AI 排序首页 | **59.7 ms** | 63.4 ms | 3 万行全表排序 |
| stats | 18.4 ms | 19.6 ms | 多次全表聚合 |
| facets | 0.6 ms | 1.8 ms | 正常 |

对照 `scripts/bench-review.mjs` 的纯 SQL 基准：COUNT 约 10 ms，深页旧写法 26 ms → 复用总数后 16 ms，AI JOIN 约 11 ms。IPC + 200 行映射又增加了 20–50 ms。

### 3.4 3 万条滚动

- 40 次跳转覆盖 18,824 px，用时 270 ms；当前文档节点稳定，虚拟化生效。
- 高刷屏下 600 ms 记录 87 帧，未见掉帧卡顿。
- 详情面板打开后节点增加约 100–150 个，属于面板本身，不是泄漏。

## 四、瓶颈与建议（按优先级）

### P0 · 导入吞吐（约 6 张/秒）

**建议**

1. dHash 改从 1280 底图计算，或把底图与 dHash 合并为一次解码。需要给指纹加版本（例如 `hash_version = 2`），旧记录继续用旧指纹，新记录用新算法，避免全库重算。
2. 导入并发从当前值逐步试到 6–8（先测内存峰值），缩略图 high 保持按需生成。
3. 批量写库已经按 50 条事务提交，可保留；瓶颈不在写库。

**预期**：单张降到 70–90 ms，3 万张从约 90 分钟降到 40 分钟左右。

### P1 · AI 排序 60 ms

`src/main/repo.ts:431-458` 的 `ORDER BY coalesce(qs.overall, -1)` 需要把 3 万行全部排序，LEFT JOIN 只是去掉了逐行子查询，排序本身没有索引可用。

**建议**：物化 `items.ai_score`（或 `quality_scores` 里冗余一份排序键）并建索引，schema 升到下一版时迁移一次；或者先取 `quality_scores` 的 top-N id，再回表拿 200 条。

### P1 · 深页 40 ms

`LIMIT 200 OFFSET 29600` 需要扫描并丢弃 2.96 万行。

**建议**：列表加载改键集分页（`WHERE (added_at, id) < (?, ?)`），IPC 增加游标参数；首屏与筛选变化仍走 offset 0。改动会影响 `Api.listItems`，建议单独排期。

### P2 · stats 18 ms

统计每次 tick 都可能触发（已有 300 ms 防抖），导入完成时会连打几次。

**建议**：给 stats 加 2–5 秒缓存，并在导入/删除/恢复后主动失效；或拆成「总数」与「聚合」两个接口，元数据按需刷新。

### P2 · 主进程内存

250 MB 对 3 万条元数据是合理的。主要组成是 Electron 基线、SQLite 页缓存与 sharp/libvips 缓存（默认约 50 MB）。批量导入时可以提高 `sharp` 并发但限制缓存，避免峰值继续上涨。

**不建议**为了降 20–30 MB 去关 WAL 或缩 SQLite 缓存，收益小、风险高。

### P2 · 监听器计数

CDP 统计的监听器从 571 涨到 1454，但当前文档节点稳定、heap 回落，判断为跨文档统计 + React 按元素注册的拖拽/双击/右键监听，不是泄漏。若后续要确认，用 heap snapshot 对比更可靠。

## 五、健康项（无需处理）

- 虚拟滚动：3 万条只渲染 18–40 张卡片，当前文档节点 < 600。
- 灯箱：打开/关闭 heap 与 DOM 均回落，无累积。
- 列表总数缓存、异步 rescan、缩略图路径缓存、EXIF 单次解析都还在。
- 首屏 10 ms、搜索 21 ms、facets < 2 ms，3 万条规模下体验没问题。
- 主进程 JS heap 仅 13–18 MB，没有大对象驻留。

## 六、尚未覆盖的风险

| 项 | 估算 / 说明 |
| --- | --- |
| CLIP 语义索引 | 3 万 × 512 float32 ≈ 61 MB；缓存扩容可能接近 90 MB；onnxruntime 会话与模型另计，预计 +200–400 MB |
| 选片导出 | 最多 999 张，缩图后 base64 内嵌单个 HTML，峰值可能数百 MB（`pick.ts:27,111,233`） |
| 备份 | `readFileSync` 把库和缩略图整份读进内存（`backup.ts:29,56`），大缓存时峰值高 |
| 缩略图统计/清理 | 遍历约 9 万个文件逐个 `stat`（`thumbs.ts`），首次统计会慢 |
| RAW 导入 | 会额外写全尺寸预览，单张耗时与内存都高于 JPEG |

这些不属于当前 3 万条 JPEG 的主路径，建议按使用频率决定是否优化。

## 七、复现方式

```bash
node scripts/perf-check.mjs          # 3 万条端到端：查询、滚动、灯箱、内存
node scripts/bench-review.mjs        # 纯 SQL 对照：深页、ai 排序、堆叠计数
node scripts/bench-import.mjs --count 40 --batches 3               # 1MP 导入吞吐
node scripts/bench-import.mjs --count 20 --width 4032 --height 3024 --noise  # 12MP 导入吞吐
```

脚本会创建临时数据目录并导入临时图片，输出结果写到 `.smoke/` 或 `.trae/smoke-shots/`，不会碰现有图库。

> 注意：脚本会启动 Electron 窗口，测量期间不要操作该窗口。

## 八、修复后复测（导入 + AI 排序）

已按 P0/P1 建议落地：导入改为「文件只读一次 + 整张图只解码一次（dHash 复用 960 底图）」，worker 4 → 6；AI 排序把分数物化到 `items.ai_score` 并建 `(ai_score DESC, added_at DESC)` 索引，schema 升到 v6。

### 8.1 导入吞吐（本机 i7-12700KF，20 线程）

| 场景 | 修复前 | 修复后 | 提升 |
| --- | --- | --- | --- |
| 1200×800 JPEG（40 张，第二批起） | 29.6 ms/张 | **10.6 ms/张** | 2.8× |
| 4032×3024 JPEG（20 张，第二批） | 53.7 ms/张 | **29.8 ms/张** | 1.8× |
| 4032×3024 JPEG（20 张，首批含预热） | 62.0 ms/张 | **43.7 ms/张** | 1.4× |

首张仍要付 sharp/libvips 预热成本；稳定吞吐按第二批起看。按报告里的 3 万张估算，从约 90 分钟降到约 30–40 分钟（取决于原图尺寸）。

### 8.2 查询（3 万条，IPC 端到端）

| 查询 | 修复前 P50 | 修复后 P50 | 说明 |
| --- | --- | --- | --- |
| AI 排序首页 | 59.7 ms | **4.8 ms** | 走 `items.ai_score` 索引，不再 JOIN + 全表排序 |
| 首页 200 条 | 9.6 ms | **5.0 ms** | 机器状态差异，量级不变 |
| 深页 29600 | 37.8 ms | **19.4 ms** | 仍是 OFFSET，键集分页未做 |
| 搜索 `photo-29` | 17.8 ms | **9.1 ms** | 同上 |
| stats | 18.4 ms | **9.2 ms** | 未加缓存，仅运行差异 |

纯 SQL 层 AI 排序：11.3 ms → **1.06 ms（10.7×）**，与端到端趋势一致。

### 8.3 兼容性说明

- dHash 改为从 960 底图计算，但保持**未按 EXIF 摆正**的像素方向，和旧库指纹同向；实测普通照片新旧指纹汉明距离 0–3（重复判定阈值 6、重定位阈值 4），旧记录不重算。
- 缩略图改为从 raw 底图按 orientation 手动摆正，8 种 EXIF 方向与 sharp 自动摆正逐像素一致（meanDiff = 0），透明 PNG 保留 alpha。
- AI 分数写入仍走 `quality_scores`，同一事务同步 `items.ai_score`；v6 迁移会给老库回填，未评分记为 -1。
- FTS 触发器收敛为 `AFTER UPDATE OF name, note, url`，改评分/旗标不再重写索引。
