# 存照 · 开发协作规则

> 目标：**减少返工、避免功能回归、保证 Windows 与 Mac 双端体验一致**
> 版本：2026-11-17 · 适用于「存照（lunaris）」项目 · 人 + AI 协作者共同遵守

---

## 怎么用这份规则

**优先级含义**

| 级别 | 含义 | 违反后果 |
| --- | --- | --- |
| **P0 红线** | 违反即造成返工、功能回归或数据事故 | 停下重来，不接受"下次注意" |
| **P1 重要** | 影响质量与双端一致性 | 提交前必须自查，缺失需在交付说明里写明"未覆盖原因" |
| **P2 建议** | 提升协作效率 | 可酌情，但连续违反说明习惯要改 |

**冲突裁决顺序**（三条撞车时按此决策）

1. 数据安全 > 一切
2. 不回归 > 新功能
3. 双端一致 > 单端最优
4. 可验证 > 可解释

**标注说明**：`【原有】` = 保留主人原规则原意；`【强化】` = 原意基础上补检查标准；`【新增】` = 新补。

---

## P0 · 红线

### R1 大改先出方案，不直接改代码 【原有】

**规则**：涉及界面或功能的优化、重构、大改，先说明要改哪些地方、影响范围、风险、替代方案，最好附带图片或示意图展示预期效果。方案确认后再动代码。

**适用场景**：改视觉风格、调整布局结构、重组交互流程、替换技术方案、重构超过 2 个文件。

**检查标准**：方案必须包含 5 项，缺一项即不合格 ——
① 改动点清单（精确到 `文件:行号`）② 影响面（哪些页面/进程/数据受影响）③ 风险与最坏结果 ④ **至少一个"不改"的替代方案** ⑤ 验收方式。
其中 ④ 最容易漏：只给一个方案等于没做取舍。

---

### R2 改动边界：只碰需求覆盖的文件 【新增】

**规则**：只改需求明确涉及的文件。看到无关代码有问题，**记录不修**，在交付说明里单列"顺带发现"。

**适用场景**：所有代码改动，尤其是「顺手优化一下」的冲动。

**检查标准**：`git diff --stat` 里的每个文件都能对应到需求条目。出现无法对应却改了的文件，视为越界，需回退或单独说明理由。

> 反例：修灯箱分界线时顺手重构了 `App.tsx` 的布局容器，导致 review 无法聚焦。

---

### R3 分批落地，每批独立可验证 【新增】

**规则**：大改拆成 2–3 批，每批自身可编译、可运行、可回滚、能独立看到效果。不追求一次改完。

**适用场景**：超过 3 个文件的改动、涉及主进程 + 渲染层的联动改动、需要重建数据的改动。

**检查标准**：每批交付时能回答「如果只保留这一批，app 是什么样」。答不上来说明批次切分不合格。

> 正例：灯箱沉浸化拆成「黑底+去容器（1h，风险低）→ 控件收敛 → 无障碍状态机」三批，第一批就能看到 80% 变化。

---

### R4 同一文件禁止并发写入 【新增】

**规则**：一个文件在同一时间只能有一个执行者在改。多方协作时先声明占用，改完再交还。

**适用场景**：人 + AI 同时改同一文件、多个 AI 会话并行、IDE 里开着未保存的改动。

**检查标准**：动手前 `git status` + 文件修改时间双重确认。发现目标文件已被改动且不是自己改的，**先停下问，不要覆盖**。

> 反例：误判对方卡住，直接写同名文件覆盖，导致 20 分钟产出丢失，双方互相覆盖两轮。

---

### R5 改前备份，改后可回滚 【新增】

**规则**：改动核心文件（主进程、数据库、灯箱等大组件）前，备份到 `.cache/backup-<文件名>-<时分>.tsx`（该目录已在 `.gitignore` 中）。

**适用场景**：单文件超过 500 行、无测试覆盖、他人正在协作、改动涉及删除逻辑。

**检查标准**：能在一分钟内恢复到改动前状态。恢复方法要写进交付说明。

---

### R6 数据安全高于一切 【新增】

**规则**：任何涉及**导入、移动、覆盖、删除**照片或其元数据的改动，必须先说明"操作失败时数据会怎样"。

**适用场景**：批量操作、路径重定位、格式转换、清理逻辑、数据库迁移、导出覆盖。

**检查标准**：① 明确失败回滚路径 ② 不产生"删了原图又没写成"的中间态 ③ 涉及不可逆操作必须有二次确认 ④ 迁移脚本幂等，老库直接可用。
**绝对禁止**：为了让测试通过而放宽容错，导致本该失败的操作用户无感知地"成功"了。

> 这个 app 的承诺是「照片不搬家、原图不动」。任何破坏这条的改动都按事故处理。

---

### R7 性能优化必须带基线数据 【原有 2 · 强化】

**规则**：性能优化必须先测基线，再改，再对比。检查是否影响现有功能、交互、兼容性和稳定性，并给出验证方式。**禁止「我觉得更快了」**。

**适用场景**：查询、渲染、索引、导出、启动耗时、内存占用、包体积。

**检查标准**：交付必须带三组数字 —— ① 改前 ② 改后 ③ 测量方法（命令 + 数据规模）。
另外必须回答：**在什么规模下会退化**（1 千张 / 3 万张 / 10 万张）。

> 反例：只说"加了索引应该很快"，没测 3 万张真实库，上线后发现首次检索要 2 秒。

---

### R8 不许用样式「藏」功能来绕过问题 【新增】

**规则**：遇到元素冲突、层级错乱、状态难管，改结构或改数据流。**不许用 `opacity: 0`、`pointer-events: none`、`inert`、`aria-hidden`、`display: none` 把问题盖住**——除非这本身就是设计意图（自动隐藏的浮层）。

**适用场景**：z-index 打架、控件遮挡、状态切换、无障碍相关。

**检查标准**：问一句「键盘用户和读屏用户还能用这个功能吗」。答不能，就是引入了回归。

> 反例：用 `inert` 实现控件自动隐藏，等于把工具从 Tab 序列和读屏树里删掉。

## P1 · 重要：质量与双端一致

### R9 双端差异：平台判断只走 `platform.ts` 【原有 3 · 强化】

**规则**：注意识别 Windows 与 Mac 的差异 —— 路径、快捷键、字体渲染、窗口行为、权限、安装/更新方式。**平台判断一律 `import { isMac, isWindows, modLabel } from '../main/platform'`，禁止在业务代码里散落 `process.platform`。**

**适用场景**：任何窗口、菜单、快捷键、路径、字体、安装相关的改动。

**检查标准**：`grep -rn "process.platform" src/` 在业务代码里应为 0 处（`platform.ts` 自身除外）。

> 项目已有明文铁律：「平台差异只在这里出现一次」。上一轮改灯箱时在 `ipc.ts` 写了 3 处 `process.platform`，违反了它，已修正。

---

### R10 双端差异清单（本项目已知点） 【强化】

**规则**：改这些地方必须显式回答「Mac 上是什么样」。

| 差异点 | Windows | macOS |
| --- | --- | --- |
| 窗口按钮 | `titleBarOverlay` 三键（右上） | 红绿灯（左上），`trafficLightPosition` |
| 标题栏禁区 | 右侧 **148px** 不可放可点元素 | 左侧 **78px** 死区 |
| 沉浸隐藏按钮 | 只能改 overlay 颜色（`symbolColor` 与底色同色） | `setWindowButtonVisibility(false)` |
| 快捷键 | `Ctrl` | `⌘`，文案用 `modLabel` |
| 字体 | Segoe UI / 微软雅黑 | PingFang SC |
| 打包 | NSIS（`npm run dist`） | dmg（`npm run dist:mac`）+ 签名公证 |
| 路径 | 盘符 + 反斜杠，注意长路径与中文路径 | 正斜杠，注意沙盒权限 |
| 关闭行为 | 关窗即退出 | 关窗不退（`if (!isMac) app.quit()`） |

**检查标准**：PR/交付说明里有一行「Mac 影响」；无 Mac 真机时写明「静态检查通过，未实机验证」，**不许默认"应该一样"**。

---

### R11 四套皮肤矩阵 【新增】

**规则**：`styles.css` 有 5 个变量块（`:root` 深色默认 / `light` / `night` / `paper` / `contrast`）。改任何配色、对比度、透明度，四套皮肤都要看。

**适用场景**：颜色、阴影、边框、浮层透明度、状态色。

**检查标准**：① 四套皮肤截图或目视记录 ② `npm run check:contrast` 通过 ③ 颜色一律走 `var(--xxx)`，无硬编码色值。

> 反例：灯箱箭头写 `bg-white/8 + text-white/80`，在浅米皮肤上几乎看不见——写死色只在深色主题下"碰巧对"。

---

### R12 核心路径回归清单 【新增】

**规则**：大改后过一遍主流程，任何一步不对就算回归。

```
导入照片 → 浏览/筛选 → 打星挑片 → 生成选片页 → 客户回传 →
只看客户选的 → 导出成品 → 换图库 → 重启后数据还在
```

**适用场景**：涉及数据库、IPC、图库管理、导出的改动。

**检查标准**：每条路径都点过一遍，结果写进交付说明。**至少覆盖"改动的功能 + 它上下游各一步"**。

---

### R13 四种状态都要设计 【新增】

**规则**：每个界面/控件都要想清楚 **空态 / 加载中 / 错误 / 超长内容** 四种状态，不能只做"有数据"那一种。

**适用场景**：列表、面板、卡片、浮层、状态条。

**检查标准**：四种状态各有明确表现。**没有数据时不要显示占位符垃圾**。

> 反例：灯箱底左长期显示 `f/— — ISO — 没有器材信息` 四个占位符，没有器材信息时应该整条不渲染。

---

### R14 可访问性底线 【新增】

**规则**：键盘可达、对比度达标、尊重减少动效。

**适用场景**：所有交互控件、自动隐藏、动效、颜色语义。

**检查标准**：
① 所有功能可纯键盘完成，控件常驻 DOM 与 a11y 树（用 `opacity` + `pointer-events-none`，不用 `inert`）
② 文字对比度：静止态 ≥3:1，交互/聚焦态 ≥4.5:1
③ `prefers-reduced-motion` 下动效改瞬时
④ 焦点环清晰可见，不被容器裁切

## P2 · 建议：提效

### R15 先读后写 【新增】

**规则**：改文件前先完整读目标文件（或至少读改动区域 ±50 行），不要凭记忆写。

**适用场景**：所有代码改动。

**检查标准**：说得出改动点前后的实际代码。说不出来就是没读。

---

### R16 引用必须真实 【新增】

**规则**：行号、函数名、变量名、API 名必须来自实际读取。不确定就说"需要确认"，**禁止编造**。

**适用场景**：方案文档、施工说明、代码 review、给他人（或 AI）的指令。

**检查标准**：交付里每个 `文件:行号` 都能对上。抽查 3 处，错 1 处就算不合格。

---

### R17 一次提交一件事 【新增】

**规则**：一个 commit / 一次交付只做一件事。修 bug 和加功能分开，格式化和逻辑改动分开。

**适用场景**：所有提交。

**检查标准**：commit message 一句话说得清。说不清就是混了。

---

### R18 改行为同步改测试与文档 【新增】

**规则**：改了状态机、筛选、排序、导出这类纯逻辑，同步更新测试；改了用户可见行为，同步更新 `docs/` 对应文档。

**适用场景**：行为变更、UI 文案变更、交互流程变更。

**检查标准**：`npm run typecheck` + `npm test` 全绿；`docs/` 里找不到描述旧行为的段落。

## 交付前自查清单（贴在手边）

```
[ ] 改动范围能对应到需求条目（R2）
[ ] 大改走了方案确认流程（R1）
[ ] 分批落地，每批可独立验证（R3）
[ ] 关键文件有备份（R5）
[ ] 没有用样式"藏"功能（R8）
[ ] 平台判断走 platform.ts，无散落 process.platform（R9）
[ ] 写了"Mac 影响"一行（R10）
[ ] 四套皮肤都看过（R11）
[ ] 核心路径回归过（R12）
[ ] 空/加载/错误/超长四种状态都有表现（R13）
[ ] 键盘可用、对比度达标（R14）
[ ] typecheck + test 全绿（R18）
[ ] 引用的行号/函数名真实（R16）
```

## 怎么落地到 Trae

这套规则的 P0 部分建议进 `.trae/rules/` 让它自动生效（`alwaysApply: true`，需精炼）；完整版留在 `docs/` 供人工 review 时对照。

拆分建议：

| 文档 | 放哪 | 生效方式 |
| --- | --- | --- |
| P0 红线（R1–R8） | `.trae/rules/05-协作红线.md` | `alwaysApply: true` |
| 双端清单（R9–R10） | 并入 `.trae/rules/10-主进程与数据.md` | `globs: src/main/**,src/preload/**` |
| 皮肤/状态/可访问性（R11–R14） | 并入 `.trae/rules/20-界面与样式.md` | `globs: src/renderer/**` |
| 测试与自证（R18） | 并入 `.trae/rules/30-测试与验证.md` | `globs: **/*.test.ts` |
| 完整版（本文） | `docs/开发协作规则.md` | 人工对照 |

> 注意：`alwaysApply` 的规则会**全量进上下文**，所以进 `.trae/rules` 的版本要压缩到一屏内，细节留在本文。
