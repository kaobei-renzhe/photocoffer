# 数据安全与迁移方案

> 触发问题：用户卸载或重装了 APP，影响重新使用吗？
>
> **结论：正常卸载重装不影响。** 关键数据都不在程序目录里，而且整理成果（标签 / 维度 / 笔记 / 评分）全在 `library.db` 里，不在配置里——**就算配置全丢，整理的心血一点不丢**。
>
> 但有 4 个风险，其中 1 个会真的丢东西（模型），需要修。

---

## 1. 数据分布（实测）

| 数据 | 位置 | 大小 | 卸载重装 |
| --- | --- | --- | --- |
| 照片原图 | 用户自己的文件夹（如 `E:\照片`） | 数十 GB | ✅ 完全无关 |
| **图库元数据**：items / tags / facets / photo_notes / quality_scores / embeddings | `<图库>\img_cache\library.db` | 数百 MB | ✅ 不受影响 |
| 缩略图 | `<图库>\img_cache\thumbnails` | 数 GB | ✅ 不受影响 |
| 应用配置 | `%APPDATA%\lunaris\config.json` | 1.3 KB | ✅ 保留 |
| 装备库 | `%APPDATA%\lunaris\gear.json` | 306 B | ✅ 保留 |
| API Key（DPAPI 加密） | `%APPDATA%\lunaris\llm-key.bin` | 66 B | ✅ 同机同用户可解密 |
| 日志 | `%APPDATA%\lunaris\logs` | 56 KB | ✅ 保留 |
| **CLIP 模型** | ⚠️ `%APPDATA%\image-nest\models\chinese-clip` | **183 MB** | **旧目录，见风险 1** |

### 为什么不会丢

`package.json` 的 `build.nsis` 里**没有** `deleteAppDataOnUninstall`，electron-builder 默认是 `false`——卸载器不会碰 `%APPDATA%`。

### config.json 里有什么（14 个字段）

```
library            当前图库路径 E:\照片
libraryIndex       图库 → 索引目录的映射
libraries          多图库注册表（含 UUID）
llm                AI 模型配置（不含密钥）
autoTag            自动分类阈值与类目
theme / skin       主题与皮肤
layout             侧栏 / 详情面板宽度
importOptions      导入选项
thumbCacheLimitMB  缩略图缓存上限
xmp                XMP 侧车开关
aiScoreMinRating   AI 评分最低星级
aiFolderIds        AI 作用范围
```

**注意**：没有一项是"整理成果"。标签、维度、笔记、评分全在 `library.db`。这是这套架构最值钱的地方——配置只是偏好，成果在库里。

## 2. 四个风险

### 风险 1：模型还在旧目录（唯一会真丢东西的）

改名时 `index.ts` 的迁移逻辑**特意跳过了 models 目录**（183 MB 复制不划算），靠 `candidates()` 的遗留目录回退去读：

```ts
// src/main/clip/models.ts:115
list.push(modelDirFor(id))                                    // lunaris/models（空）
for (const name of LEGACY_APP_DIRS)                           // image-nest / moonnest / 月巢
  list.push(join(appData, name, 'models', 'chinese-clip'))    // ← 实际读这里
```

**后果**：卸载旧版「月巢」时勾了"删除个人数据"，或者清理软件把 `image-nest` 当"已卸载程序的残留"扫掉 → 模型消失 → 重装后首次语义搜索要重新下 183 MB。

**能恢复**（`download.ts` 会自动下），但会卡一阵，而且用户不知道在等什么。

### 风险 2：旧版不会自动升级

`appId` 从 `com.silvermoon.moonnest` 改成了 `com.silvermoon.lunaris`，所以旧「月巢」和新「月相」会**并存**，不是覆盖安装。旧数据留在旧目录里，不会被新版本读到（除了模型靠回退）。

### 风险 3：换电脑没有任何迁移手段

图库目录拷过去能重新打开（标签维度都在 db 里），但：
- AI 模型配置要重填
- API Key 要重填（DPAPI 换机解不开，这是设计如此）
- 主题、皮肤、布局要重设
- 装备库要重录

### 风险 4：图库路径失效的处理是对的（不用改）

`ipc.ts:298` 的 `library:last` 在索引目录不在时返回 `indexMissing`，注释写着「别让用户以为图库凭空消失」。多图库列表也有 `missing` / `index-missing` / `ok` 三态。

这块已经做对了，**不要动**。

## 3. 四项改进

### P1 · 模型搬到当前 userData（半天）

**目标**：`%APPDATA%\lunaris\models\chinese-clip` 成为真实位置，不再依赖旧目录回退。

```ts
// src/main/index.ts，在初始化 db / clip 之前调用
// 复用 models.ts 现成的 resolveModelDir：它本来就会按 candidates() 顺序找第一个「文件齐全且大小对得上」的目录
function migrateModelDir(): void {
  const targetRoot = join(app.getPath('userData'), 'models')
  const appData = app.getPath('appData')

  for (const id of Object.keys(EMBEDDING_MODELS) as EmbeddingModelId[]) {
    const spec = EMBEDDING_MODELS[id]
    const target = join(targetRoot, spec.dirName)
    const source = resolveModelDir(id)

    // source 为 null（没下过）或已经是目标目录 → 都跳过
    if (!source || source === target) continue

    mkdirSync(targetRoot, { recursive: true })
    try {
      renameSync(source, target)                     // 同盘：秒完成
    } catch {
      cpSync(source, target, { recursive: true })    // 跨盘 EXDEV：降级为复制
      rmSync(source, { recursive: true, force: true })
    }
    void log.info('clip', '模型已迁到当前数据目录', { id, from: source, to: target })
  }
}
```

**三个必须注意的点**：

1. **`renameSync` 跨盘会抛 `EXDEV`**，必须 try/catch 降级为 `cpSync`，否则用户在"图库在 D 盘、AppData 在 C 盘"的配置下会直接失败。
2. **`resolveModelDir` 已经处理了"目标已有完整模型"的情况**——它会先查 `modelDirFor(id)`（即目标），所以 `source === target` 时自动跳过，不用另写判断。
3. **搬完要打日志**，用户出问题时能查到"模型去哪了"。

> 注意 `resolveModelDir` 现在是 `export` 的，`modelDirFor` 也是，直接 import 即可，不用改 `models.ts`。

**不搬的替代方案**：把 `candidates()` 的顺序改成"新目录优先"（已经是了），并在设置里显示"模型位置：旧目录"——但这只是把问题可视化，隐患还在。

### P2 · 配置导出 / 导入（1 天）

**目标**：换电脑时一条命令恢复，不用重设一遍。

#### 导出

一个 JSON 文件，**不含 API Key**：

```json
{
  "app": "lunaris",
  "format": 1,
  "exportedAt": 1762758000000,
  "config": { "theme": "system", "skin": "classic", "layout": {...}, "autoTag": {...},
              "importOptions": {...}, "thumbCacheLimitMB": 10240,
              "xmp": {...}, "aiScoreMinRating": 3, "llm": { ...不含 key... } },
  "gear": { ... }
}
```

**明确不导出**的：
- `llm-key.bin` —— 加密密钥，换机解不开，导出去也是废的
- `library` / `libraries` —— 路径是机器相关的，导过去反而会指向不存在的目录
- `library.db` —— 跟着图库目录走，不用导

#### 导入

```
读 JSON → 校验 app 字段和 format 版本
→ 逐字段合并（不整个替换，避免吃掉用户已有的新设置）
→ 跳过 library / libraries
→ 如果 llm.models 有内容但没 key，提示「模型配置已导入，请重新填写 API Key」
→ 提示「图库需要重新选择：点这里打开图库」
```

**UI 位置**：设置 → 通用 → 最底部，两个按钮并列。

**为什么合并而不是替换**：用户可能在新机器上已经配好了一部分（比如换了新主题），整个替换会把它冲掉。

### P3 · 关于页显示数据位置（半天）

```
数据位置
  照片与图库索引    E:\照片\img_cache\            [打开]
  应用设置          %APPDATA%\lunaris\            [打开]
  AI 模型（183 MB） %APPDATA%\lunaris\models\     [打开]

  卸载「月相」不会删除以上任何文件。
  整理成果（标签、维度、笔记、评分）保存在图库索引里，
  备份图库目录就等于备份了全部整理结果。
```

最后两句话是重点：**告诉用户该备份什么**。大多数"数据丢了"的恐慌来自不知道数据在哪。

### P4 · 卸载提示（不做 NSIS，写文档）

改 NSIS 自定义页要学 `nsDialogs` + 维护脚本，性价比低。

替代做法：把「卸载不会删除你的照片和图库」写进三处——
1. 关于页（P3 里已经有了）
2. `README.md` 的安装章节
3. 安装完成页的一句文案（`nsis.oneClick: false`，可以在 finish 页加文字）

## 4. 三个迁移场景怎么做

### 场景 A：同机卸载重装

```
1. 正常卸载（不勾"删除个人数据"）
2. 装新版
3. 打开 → 自动恢复上次图库、主题、AI 配置
```

**不需要任何操作。** 如果 P1 做了，模型也不用重下。

### 场景 B：换电脑

```
旧机：设置 → 通用 → 导出配置 → 得到 lunaris-settings.json
      （图库目录整个拷到移动硬盘，包括 img_cache 子目录）

新机：装月相 → 先"打开图库"选到拷贝过来的目录
      → 设置 → 导入配置 → 选那个 json
      → 重新填 API Key
      → 首次语义搜索会重新下载模型（183 MB）
```

**要重做的只有 API Key 和模型下载**，标签、维度、笔记、评分全在图库里。

### 场景 C：图库换了盘符或改了名

多图库方案里已经设计了用 UUID 认库（存在 `library.db` 的 `meta` 表）。路径变了之后：
- 从图库列表点进去 → 提示 `missing`
- 用户重新选目录 → 读 `meta` 里的 UUID 对上 → 认回同一个库

**这个能力已经在 `libraries.ts` 里实现了**，P 系列改动不影响它。

## 5. 明确不做的

| 别做 | 原因 |
| --- | --- |
| 把 API Key 也导出 | DPAPI 换机解不开，导出去是废文件；明文导出更不行 |
| 导出 `library.db` | 几百 MB 到几 GB，且随时在变。备份图库目录才是正道 |
| 做云端自动备份 | 要账号、要服务器、要处理隐私，和"本地优先"的定位冲突 |
| 改 NSIS 自定义卸载页 | 成本高于收益，写清文档 + 关于页就够 |
| 把模型打进安装包 | 安装包从 145 MB 涨到 330 MB，且模型可以按需下 |
| 迁移时静默删除旧目录 | 万一新版有问题，用户还能回滚到旧版。**只搬模型，不碰旧配置** |
