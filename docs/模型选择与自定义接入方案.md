# 模型选择与自定义接入方案

> 触发问题：「可以让用户自己选择下载内置模型，或接入自己的自定义模型吗？」
> 依据：`docs/本地语义模型效果实测报告.md`（2026-11-16 实测）
> 结论先说：**内置模型选择已经有了**；**自定义模型可以做，但不是当前最该做的**——先修结果收敛，收益大 10 倍。

---

## 0. 现状盘点

### 已经有的（不用重做）

| 能力 | 实现位置 | 说明 |
| --- | --- | --- |
| **双模型定义** | `src/main/clip/models.ts` `EMBEDDING_MODELS` | Chinese-CLIP（512 维 / 190 MB）+ SigLIP 2（768 维 / 412 MB） |
| **模型选择 UI** | `SettingsDialog.tsx:1450` | 列表 + 下载 + 切换 + 状态提示都有 |
| **多模型向量共存** | `embeddings` 表 | `PRIMARY KEY (item_id, model)`，两套向量互不打架 |
| **换模型不丢旧索引** | `switchModel()` | 切过去只提示「还有 N 张需要重建索引」，旧的不删 |
| **下载器** | `src/main/clip/download.ts` | **断点续传（Range）+ 大小校验 + 失败清 `.part` + 进度回调**，质量不错 |
| **模型信息接口** | `EmbeddingModelInfo` | id / label / note / bytes / dim / ready / active / indexed / total |

> 也就是说：「用户自己选择下载内置模型」这件事**已经做完了**，只是扩模型数量的问题。

### 没有的

| 缺口 | 现状 |
| --- | --- |
| **自定义模型导入** | 模型规格全硬编码在 `EMBEDDING_MODELS`，用户加不了 |
| **结果收敛** | ⭐ 最严重。搜什么都返回 30409 张，没有条数控制 |
| **模型适用场景说明** | `note` 字段只有一句话，用户不知道"什么时候该选哪个" |
| **下载流程端到端验证** | 模型一直躺在开发仓库里，**真实下载路径没跑通过**（见实测报告 §6） |

---

## 1. 优先级判断：先修效果，再扩模型

实测数据显示：**换模型的边际收益远小于修搜索体验**。

| 做的事 | 用户感知提升 | 工时 |
| --- | --- | --- |
| 结果收敛（top 200） | ⭐⭐⭐⭐⭐ 搜"一只猫"不再翻出 3 万张噪音 | 半天 |
| 验证真实下载 | ⭐⭐⭐⭐ 决定新用户能不能用上语义搜索 | 半天 |
| 分类降级为弱提示 | ⭐⭐⭐ 避免用户被 0.4 分的标签误导 | 2 小时 |
| 多接 2 个内置模型 | ⭐⭐ 都是 CLIP 系，能力相近 | 1–2 天 |
| 支持自定义 ONNX | ⭐ 只有折腾党用得上 | 3–5 天 |

**所以推荐顺序：L0 → L1 →（L3 试点）→ L2**。

---

## 2. L0 · 结果收敛（最优先，半天）

### 问题

`searchByText(query, filter, limit=200, offset=0)` 的 `limit` 只控制**分页大小**，`total` 仍是全库命中数（30409）。UI 把 `total` 直接展示，用户看到「找到 30409 张」。

### 实测依据

top1 → top500 分数只衰减 9–15%，**绝对阈值不可行**：

| 绝对阈值 | 后果 |
| --- | --- |
| 0.45 | 「花」(0.431)、「一只猫」(0.440) 的 top1 都被砍掉 |
| 0.40 | 3 万张里几千张能过，等于没过滤 |

相对阈值 `score ≥ top1 × 0.95` 能收敛到 top 10–100，但**跨度仍然很大**（泛化词天然有很多正确答案）。

### 方案：固定条数三档，不暴露阈值

| 档位 | 返回条数 | 用于 |
| --- | --- | --- |
| **精确** | top 50 | 只想看最像的几张 |
| **标准**（默认） | **top 200** | 日常搜图 |
| **全部** | 不限（现有行为） | 找素材、做筛选 |

### 改动点

**① `src/main/embeddings.ts` `searchByText`**

```ts
// 新增 cap 参数，默认 200
export async function searchByText(
  query: string,
  filter: FilterState,
  limit = 200,
  offset = 0,
  cap = 200          // ← 新增：结果上限，0 或 Infinity 表示不限
): Promise<ClipSearchResult> {
  const text = query.trim()
  if (!text) return { items: [], scores: [], total: 0 }
  const model = activeModel()
  const vector = await embedText(text)
  const key = `text|${model.tag}|${text}|${JSON.stringify({ ...filter, query: '' })}`
  const ranked = await rankedAll(vector, filter, undefined, key)
  // 关键：total 也跟着收敛，否则 UI 还是显示 30409
  const capped = cap > 0 ? { ids: ranked.ids.slice(0, cap), scores: ranked.scores.slice(0, cap) } : ranked
  return pageResult(capped, limit, offset)
}
```

**② IPC 层**：`src/main/ipc.ts:1441` 的 `clip:searchText` handler 把 `cap` 透传（现在是 `(query, filter, limit?, offset?)`，要加第 5 个参数）

**③ preload 桥**：`src/preload/index.ts:178` 的桥接函数也要加参数

```ts
// 改前
searchText: (query, filter, limit?, offset?) =>
  ipcRenderer.invoke('clip:searchText', query, filter, limit, offset),

// 改后
searchText: (query, filter, limit?, offset?, cap?) =>
  ipcRenderer.invoke('clip:searchText', query, filter, limit, offset, cap),
```

> 完整调用链：`渲染层 → preload/index.ts:178 → ipc.ts:1441 → embeddings.ts:521`，四处都要改，漏一处就断。

**④ 渲染层 UI**：搜索结果条区域加档位切换

```tsx
{filter.query && semanticMode && (
  <div className="flex items-center gap-1 text-[11.5px] text-[var(--faint)]">
    <span>结果</span>
    {[
      { id: 'precise', label: '精确', cap: 50 },
      { id: 'normal', label: '标准', cap: 200 },
      { id: 'all', label: '全部', cap: 0 }
    ].map((opt) => (
      <button
        key={opt.id}
        className={`rounded px-1.5 ${capMode === opt.id ? 'bg-[var(--accent-soft)] text-[var(--accent-text)]' : 'hover:bg-[var(--panel-2)]'}`}
        onClick={() => setCapMode(opt.id)}
      >
        {opt.label}
      </button>
    ))}
  </div>
)}
```

**⑤ 文案**：把「找到 30409 张」改成「最相关的 200 张（共 30409 张有向量）」

> ⭐ 关键：**不要把相似度数值显示给用户**。0.43 这种数字用户看不懂，只会怀疑"是不是没搜对"。

### 验收

- [ ] 搜「一只猫」默认只显示 200 张，不会出现"3 万张结果"
- [ ] 切「全部」能恢复现在的行为
- [ ] 搜索结果条上的档位在切查询后保持不变（记在组件状态）
- [ ] `filter.query` 清空后档位 UI 自动隐藏

## 3. L1 · 内置模型扩展与选择（1–2 天）

### 3.1 现在的问题

- 只有 2 个模型，且 `note` 一句话说不清取舍
- 用户不知道「我该选哪个」
- 下载 412 MB 的 SigLIP 2 之后发现中文更弱，会骂人

### 3.2 扩到 4 个（候选池）

| 模型 | 体积 | 维 | 中文 | 擅长 | 建议定位 |
| --- | --- | --- | --- | --- | --- |
| **Chinese-CLIP**（现有） | 190 MB | 512 | 强 | 中文物体/场景检索 | **默认**，中文用户首选 |
| **SigLIP 2**（现有） | 412 MB | 768 | 弱 | 多语言、零样本分类 | 已有，明确标注"中文类目弱" |
| **Chinese-CLIP large** | ~700 MB | 768 | 更强 | 细粒度检索 | 可选，追求准确率 |
| **jina-clip-v2** | ~1 GB | 1024 | 中英 | 长文本、多语言 | 需评估 ONNX 可用性 |

> 候选模型上线前必须做一次「8 组查询命中率」横向对比（复用实测报告的判定方法），**用数据决定要不要加**，别凭论文榜单。

### 3.3 UI 改造：从"一行说明"到"选择卡"

现在只是一行 `label + note`。改成卡片，信息分层：

```tsx
<div className="rounded-xl border border-[var(--border)] p-3">
  <div className="flex items-baseline gap-2">
    <b className="text-[13px]">{model.label}</b>
    {model.active && <span className="rounded bg-[var(--accent-soft)] px-1.5 text-[10px] text-[var(--accent-text)]">使用中</span>}
    <span className="ml-auto text-[11px] text-[var(--faint)]">{(model.bytes / 1048576).toFixed(0)} MB · {model.dim} 维</span>
  </div>
  <p className="mt-1 text-[11.5px] text-[var(--muted)]">{model.note}</p>
  <div className="mt-2 flex gap-1 text-[10.5px]">
    <span className="tag">中文 {model.zhStrength}</span>
    <span className="tag">速度 {model.speed}</span>
    <span className="tag">适合 {model.bestFor}</span>
  </div>
  <div className="mt-2 text-[11px] text-[var(--faint)]">
    已索引 {model.indexed} / {model.total} 张
    {model.indexed < model.total && model.active && '（需重建索引）'}
  </div>
</div>
```

需要在 `EmbeddingModelSpec` 里补三个字段：`zhStrength` / `speed` / `bestFor`。

### 3.4 换模型的引导（现在只有一句提示）

现在的 `switchModel` 只弹「还有 N 张需要重建索引」。补一条明确的行动指引：

```
已切换到 SigLIP 2
→ 旧模型（Chinese-CLIP）的索引已保留，随时可以切回来
→ 新模型需要重建索引：点左侧「语义索引」开始（约 31864 张，预计 2–3 小时）
→ 或者打开「设置 → 闲时自动建立」，让它慢慢跑
```

### 3.5 验收

- [ ] 4 个模型都能下、能切、能重建索引
- [ ] 每个模型卡片上有体积 / 维数 / 中文强度 / 擅长场景
- [ ] 切换后明确告知「旧索引保留 + 需要重建」
- [ ] 同一张图在不同模型下的检索结果可对比（用于横向评估）

## 4. L2 · 自定义 ONNX 导入（3–5 天，门槛高）

### 4.1 只支持一种东西：CLIP 架构的 ONNX

**必须同时具备图像塔和文本塔、且在同一向量空间**。纯图像分类模型、纯文本 embedding 模型**都不行**。

支持的输入形态：

| 形态 | 对应现在代码 | 例子 |
| --- | --- | --- |
| `combined` | 单文件含两个输入/输出 | Chinese-CLIP |
| `split` | vision + text 两个 onnx | SigLIP 2 |

### 4.2 描述符文件（用户手动填）

模型目录放一个 `clip-model.json`：

```json
{
  "id": "my-clip-2026",
  "label": "我的中文模型",
  "tag": "my-clip-2026-v1",
  "dim": 512,
  "imageSize": 224,
  "resizeFit": "cover",
  "resizeKernel": "lanczos3",
  "mean": [0.48145466, 0.4578275, 0.40821073],
  "std": [0.26862954, 0.26130258, 0.27577711],
  "maxTextLength": 52,
  "tokenizer": "bert",
  "files": {
    "combined": "model_quantized.onnx",
    "vocab": "vocab.txt"
  }
}
```

### 4.3 ⚠️ 最大的风险不是技术，是用户配错

`mean` / `std` / `imageSize` 填错，**不会报错**，但索引出来的向量全是垃圾——用户会以为"这个 app 的搜索很烂"。

**必须做的安全网**：

1. **导入时试跑校验**：用 3 张内置样图 + 5 个内置查询词跑一遍，结果相关性低于阈值就**拒绝导入**并提示"预处理参数可能不匹配"
2. **tag 强制唯一**：换了 `dim` 或预处理却复用旧 tag，新旧向量会混在一起（`models.ts` 注释里已经警告过）
3. **目录只读校验**：`files` 里声明的文件必须存在，且**建议**校验 sha256（现在的 `size` 校验只能防截断，防不了换文件）
4. **失败可回滚**：导入失败或校验不过，自动删掉半个模型目录

### 4.4 不建议做的

- ❌ 让用户"从 HuggingFace 链接自动下载 + 自动转 ONNX"——转换涉及 optimum/onnxruntime-tools，打包体积暴涨，失败率极高
- ❌ 支持任意 embedding 模型（非 CLIP 架构），代码路径完全不同
- ❌ 让用户在 UI 里填 mean/std（配错率接近 100%），只能编辑 JSON

### 4.5 谁会用

诚实评估：**极少数**。需要用户自己找到模型、转 ONNX、看懂 mean/std、填 JSON。摄影用户里愿意折腾的估计 < 1%。

**建议：等有人明确提需求再做。**

## 5. L3 · 外部 Embedding API（建议做成可选试点）

### 5.1 现实：能做图文检索的 API 很少

| 服务 | 支持图像？ | 中文 | 备注 |
| --- | --- | --- | --- |
| OpenAI `text-embedding-3` | ❌ **纯文本** | 好 | 做不了图搜，直接排除 |
| **Jina CLIP v2** | ✅ 图文同空间 | 好 | 有 API，1024 维 |
| **Cohere Embed v4** | ✅ 支持图像 | 中 | 有 API |
| **Voyage multimodal** | ✅ | 中 | 有 API |
| 阿里通义 / 智谱 | 需逐个确认 | 好 | 国内可用性好，但多为文本 embedding |

### 5.2 三个绕不过去的问题

| 问题 | 影响 |
| --- | --- |
| **隐私** | 3 万张照片要全传到云端。摄影用户对这个极敏感——这可能直接劝退核心用户 |
| **成本** | 3 万张 × 约 1000 token ≈ 3000 万 token，单次建库约 $3–15。换模型要重来一遍 |
| **离线** | 断网就搜不了，和"本地图片管理工具"的定位冲突 |

### 5.3 建议做法

- **默认关闭**，作为「高级」选项
- 只上传**缩略图**（长边 512），不上传原图
- 建库前明确告知「会把 3 万张缩略图上传到 X 服务」，需二次确认
- 只支持自己填 endpoint + key（不做硬编码服务商）

**结论**：技术可行，但和"本地优先"的产品气质冲突。建议**先不做**，等有用户明确愿意用隐私换效果。

## 6. 四条路线对比

| 层级 | 解决什么 | 工时 | 风险 | 用户覆盖 | 建议 |
| --- | --- | --- | --- | --- | --- |
| **L0 结果收敛** | 搜完不用翻 3 万张 | 半天 | 极低 | **100%** | ✅ **立刻做** |
| **L1 内置模型扩展** | 能选、选得明白 | 1–2 天 | 低 | 30%（会去设置的） | ✅ 做，但先横向实测 |
| **L2 自定义 ONNX** | 折腾党能接自己的 | 3–5 天 | **高**（配错=垃圾索引） | <1% | ⏸ 等需求 |
| **L3 外部 API** | 效果上限最高 | 3–4 天 | 中（隐私/成本） | 5–10% | ⏸ 可选试点 |

## 7. 明确不做

| 别做 | 原因 |
| --- | --- |
| 用绝对相似度阈值过滤 | 实测 top1→top500 只差 0.04–0.07，划不出干净界线（详见实测报告 §4） |
| 把相似度数值显示给用户 | 0.43 这种数字用户看不懂，只会怀疑搜错了 |
| 自动下载并转换 HuggingFace 模型 | optimum/onnx 工具链会让安装包暴涨，失败率高 |
| 支持非 CLIP 架构的 embedding 模型 | 代码路径完全不同，收益不明 |
| 在 UI 里让用户填 mean/std | 配错率接近 100%，只能编辑 JSON |
| 改 `embeddings` 表结构 | 现有 `(item_id, model)` 双主键已经能支撑多模型共存 |
| 换模型时删旧索引 | 现在会保留，是正确的；删了用户切回来要重建几小时 |
| 把 SigLIP 2 设为默认 | 注释已实测"中文类目弱于 Chinese-CLIP" |

## 一句话总结

> 用户「选内置模型」这件事**已经做完了**，缺的是**扩数量和把取舍说清楚**。
> 但真正该先做的不是模型，是**让搜索结果收敛**——现在搜什么都返回 3 万张，换再强的模型感受不到。
